# scripts/ — операции над средой и данными

Здесь живёт то, что действует **снаружи цикла разработки**: боевая БД, релиз,
деплой, служба, распространяемые артефакты, наполнение базы данными.

Второй каталог скриптов — [`tools/`](../tools/README.md) — про другое: он
исполняется **процессом разработки** (генераторы карт и метрик, гейты, git-хук,
цикл сборки). Граница проходит по тому, кто и когда скрипт запускает, а не по
языку и не по размеру.

Правило записано в `architecture.toml` (`[conventions.script_homes]`) и
**проверяется**: состав обоих каталогов перечислен правилами
`tools_dir_manifest` / `scripts_dir_manifest`, их сверяет
`powershell -File tools/check_architecture.ps1`. Новый скрипт не положить молча —
его придётся классифицировать явно. Это не бюрократия: до 2026-08-19 каталоги
перемешались именно потому, что классификацию никто не делал.

## Состав

| Файл | Назначение |
|---|---|
| `build-release.ps1` | Релизная сборка **бэкенда и фронта** → `deploy/` (ZIP + `update-release.ps1`) |
| `build-release-max.ps1` | То же с fat LTO и максимальными безопасными оптимизациями |
| `update-release.ps1` | Серверный скрипт: проверка, развёртывание и откат через Servy |
| `install-servy.ps1` | Регистрация приложения в Servy при первой установке |
| `package_ym_cash_payments_plugin.ps1` | Упаковка плагина `ym-cash-payments` в `plugins/dist/*.plugin.zip` |
| `test_data_a024_bi_indicator.sql` | Тестовые BI-индикаторы (`INSERT OR IGNORE`, безопасно повторять) |

Имена релизной цепочки — через дефис, остальные — через подчёркивание. Это не
недосмотр: `update-release.ps1` и `install-servy.ps1` уезжают на боевой сервер и
названы там в инструкции оператора, поэтому переименование стоит дороже
единообразия. Первые два зовут их по имени и держат тот же стиль.

## Снимок и восстановление базы — не здесь

Раньше в этом каталоге лежали `backup_db.ps1`, `auto_backup.ps1` и
`restore_db.ps1`. Они удалены 2026-08-19, и вот почему: база работает в режиме
**WAL**, а скрипты копировали только `app.db`, без `-wal`. Копия, снятая под
нагрузкой, — не бэкап, а файл, который выглядит как бэкап. За всё время ими не
воспользовались ни разу: в `F:\data\sdd_mpi_app\backups\` нет ни одного их
файла, только снимки, сделанные приложением.

Правильный снимок делает `VACUUM INTO` — SQLite сам собирает целостный файл.
Это уже реализовано в приложении: **«Наборы данных»** (`system/datasets/`),
снимок → gzip → S3 и обратно, потоком, с проверкой контрольной суммы. Дока —
[docs/DATASETS_TRANSFER.md](../docs/DATASETS_TRANSFER.md).

## Релиз

```powershell
.\scripts\build-release.ps1                 # обычный релиз
.\scripts\build-release-max.ps1             # fat LTO, один codegen unit, strip, panic=abort
.\scripts\build-release-max.ps1 -NativeCpu  # только если CPU сборочной и целевой машин совместимы
```

Собирается и бэкенд (`cargo build --profile release --bin backend`), и фронт
(`trunk build --cargo-profile release`). В `deploy/` остаются ровно два файла
для переноса на сервер:

```
deploy/
├── marketplace-deploy.zip   # бэкенд, фронт и миграции
└── update-release.ps1       # постоянный серверный скрипт обновления
```

Дальше: скопировать оба файла на сервер в один каталог, открыть PowerShell от
администратора и выполнить `.\update-release.ps1`. По умолчанию обновляется
`C:\Users\udv\Desktop\MPI`, имя службы Servy — `backend`.

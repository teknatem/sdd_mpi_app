# Инвентаризация знаний: метод, классификация, метрики

Как обнаружить, посчитать и классифицировать **всё**, из чего система и её LLM-чат
извлекают знание, и как отличить существующее от достижимого.

Документ нормативный: он задаёт метод и реестр поверхностей, а не отчёт. Цифры в конце —
опорные, каждая с командой, которой получена; они устаревают, метод — нет.

> **Зачем.** `/api/kb/stats` считает markdown-статьи — это примерно пятая часть того,
> откуда чат берёт знание. Реестр сущностей, источники данных, план счетов,
> quality-проверки, плагины, Процессы, Действия, навыки и каталог инструментов не
> посчитаны нигде. Пока их нет в счёте, невозможно ни оценить бюджет контекста, ни
> заметить, что курируемый корпус пуст, — а он пуст (см. «Опорные цифры»).

---

## 1. Что считается единицей

**Единица хранения/извлечения** — то, что агент получает *одним обращением* и что имеет
стабильный идентификатор.

Из определения следует главное различение, без которого подсчёт бессмыслен:

| Семейство | Примеры | Чем измеряется |
|---|---|---|
| **Хранимая единица** | статья, карта `generated`, навык, ресурс навыка, промпт ядра, определение quality-проверки, бандл плагина, определение Процесса и Этапа | штуки, байты, токены |
| **Вычисляемая поверхность** | схема сущности, источник данных `dsXX`/`dvXX`, план счетов, join-hint, произвольный SQL, прогон проверки, вызов серверного метода плагина | мощность (сколько объектов) + типичный размер ответа |

Складывать их в одно число нельзя: у хранимого есть себестоимость на диске и полный
размер, у вычисляемого — только цена конкретного ответа. Поэтому сводок всегда две.

**Правило подсчёта токенов: считать так, как доставляется, а не так, как хранится.**
`get_knowledge` отдаёт `doc.content` целиком — ни чанкинга, ни пагинации, — значит
единица бюджета равна документу, и статья на 18 000 токенов неделима. Для вычисляемой
поверхности единица бюджета — типичный ответ инструмента, замеренный на образце, а не
объём таблицы за ним.

Оценщик токенов в системе один и уже есть: `estimate_tokens`
(`shared/llm/knowledge_base.rs`) — кириллица/2.7 + латиница/4 + прочее/3. Инвентаризация
обязана пользоваться им, а не своим: иначе её числа не сойдутся с `token_cost`, который
чат видит в выдаче поиска.

## 2. Реестр поверхностей

Ядро метода. Список того, что вообще бывает, объявляется **явно** — каждая строка
приносит свой способ перечисления. Обход диска не заметит того, чего на диске нет, а на
диске нет большей части системы.

| Поверхность | Семейство | Происхождение | Область | Канал раскрытия | Как перечислить |
|---|---|---|---|---|---|
| Статьи `business` | хранимая | `file_curated` | экземпляр | внутренний чат | обход `<kb>/*.md` |
| Статьи `app` | хранимая | `code_embedded` | приложение | внутренний чат | `EMBEDDED_LLM_DOCS` |
| Карты `generated` | хранимая | `db_generated` | экземпляр | внутренний чат | `kb_generated::regenerate_all` |
| Словарь тегов | хранимая | `file_curated` | экземпляр | внутренний чат | `<kb>/_vocabulary.md` |
| Навыки и их ресурсы | хранимая | `code_embedded` + `file_curated` | приложение + экземпляр | внутренний чат | `skills::snapshot()` |
| Промпт ядра | хранимая | `code_embedded` | приложение | внутренний чат | `skills::core_prompt()` |
| Quality-проверки | хранимая | `file_curated` | приложение | внутренний чат | `quality::registry::snapshot()` |
| Плагины (бандлы) | хранимая | `db_live` | экземпляр | внутренний чат + API | `plugins::repository::list_all` |
| Процессы и Этапы | хранимая | `db_live` | экземпляр | внутренний чат + API | `processes::repository::list_*_head_records` |
| Действия | вычисляемая | `code_registry` | приложение | внутренний чат + API | `processes::actions::list()` |
| Сущности (метаданные) | вычисляемая | `code_registry` | приложение | внутренний чат + API | `ALL_ENTITIES` |
| Источники `dsXX`/`dvXX` | вычисляемая | `code_registry` | приложение | внутренний чат + API | `data_access::list_sources` |
| План счетов, обороты | вычисляемая | `code_registry` | приложение | внутренний чат + API | `ACCOUNT_REGISTRY`, `TURNOVER_CLASSES` |
| Разделы UI | вычисляемая | `code_registry` | приложение | внутренний чат + API | `SCOPE_CATALOG` |
| Регламентные задания | вычисляемая | `code_registry` | приложение + экземпляр | внутренний чат + API | реестр задач |
| Каталог инструментов | вычисляемая | `code_registry` | приложение | внутренний чат | `skills::tool_universe()` |
| Тикеты, письма, данные | вычисляемая | `db_live` | экземпляр | внутренний чат + API | SQL |

> **Правило.** Новая поверхность заводится строкой в этом реестре. Не заведена — не
> видна, и невидимость эту ничто не обнаружит: она не сломает ни сборку, ни тест.

## 3. Семь осей классификации

**A. Происхождение** — «где источник правды»:

- `code_embedded` — вшито в бинарь через `include_str!`;
- `code_registry` — Rust-константы и структуры (`ActionInfo`, `SCOPE_CATALOG`, `ALL_ENTITIES`);
- `db_generated` — собрано из БД в файл при старте;
- `file_curated` — файлы вне репозитория, правит человек;
- `db_live` — читается из БД по запросу;
- `external_api` — ответ внешнего API; знанием не хранится, только описывается статьёй.

**B. Форма хранения:** markdown · Rust-константа · строка БД · JS-модуль · JSON Schema.
Определяет, чем единицу вообще можно обнаружить (см. §4).

**C. Кто правит:** приложение (руками нельзя — `app/`, `generated/`) · куратор ·
разработчик · LLM. Без этой оси инвентаризация посоветует править то, куда запись
запрещена и вернёт ошибку.

**D. Достижимость внутренним чатом** — центральная ось:

| Уровень | Значение |
|---|---|
| `default_search` | находится обычным `search_knowledge` |
| `by_id_only` | только `get_knowledge(id)` или `corpus="generated"` |
| `tool_gated` | отдаётся лишь конкретным инструментом |
| `skill_gated` | инструмент есть, но только внутри навыка, к которому у специализации есть доступ |
| `unreachable` | ни один инструмент эту поверхность не отдаёт |

**E. Жизненный цикл:** `active` · `draft` · `deprecated` · `stale` (истёк TTL) ·
`orphaned` (строка статистики без живой статьи).

**F. Область применимости** — для какого контекста знание является истинным:

- `application` — одинаково для всех экземпляров приложения: встроенные документы,
    реестры, правила и общие описания;
- `instance` — относится к конкретной БД, конфигурации или набору данных экземпляра;
- `mixed` — общая схема или правило с экземплярными значениями;
- `external` — описание внешней системы или API.

Эта ось не совпадает с происхождением. Например, схема сущности хранится в коде и имеет
область `application`, а результат запроса к этой сущности вычисляется для `instance`.

**G. Канал раскрытия** — кому знание доступно без чтения исходного кода:

- `source_only` — существует в исходном коде, но не отдаётся никаким прикладным каналом;
- `internal_runtime` — доступно внутреннему чату или служебному инструменту;
- `external_api` — доступно клиенту через API без доступа к репозиторию;
- `both` — доступно и внутреннему чату, и внешнему API;
- `unexposed` — существует в системе, но намеренно не раскрывается.

Канал раскрытия не заменяет ось достижимости чатом: `external_api` может быть доступен
внешнему клиенту, но недоступен чату, а `tool_gated` может быть доступен чату без внешнего
API. Для каждой поверхности фиксируются оба свойства.

### Роль исходного кода

Исходный код — полноценный источник знаний системы, но не единый корпус и не канал доставки.
Его роль нужно фиксировать отдельно:

- `code_authoritative` — код является источником истины для поведения, правил, прав и
    побочных эффектов;
- `code_extracted` — из кода построен каталог, схема или документ, доступный через рантайм;
- `code_undocumented` — смысл существует в коде, но не выведен в прикладной канал.

Это свойство можно хранить как `code_role` у поверхности или вычислять из её происхождения.
Сырой исходный код не следует считать доступным знанием автоматически: разработчик с доступом
к репозиторию может его прочитать, но внутренний чат и внешний API получают только то, что
прошло через соответствующий канал раскрытия.

## 4. Метод обнаружения

Три способа, и ни один по отдельности не полон:

1. **Обход файлов** — видит markdown и JS. Не видит ничего из Rust и БД.
2. **Запрос БД** — видит плагины, Процессы, Этапы, тикеты. Не видит реестров кода.
3. **Обход реестров Rust** — единственный способ увидеть Действия, сущности, источники
   данных, счета, обороты, разделы UI и каталог инструментов.

4. **Снятие контракта внешнего API** — перечисляет поверхности, которые доступны клиенту
    без исходного кода, и фиксирует фактический размер ответа. Документация API сама по себе
    не доказывает раскрытие: маршрут должен существовать и пройти проверку доступа.

Исходный код при этом является отдельным статическим источником: он показывает
`code_authoritative` и `code_undocumented`, но не доказывает доступность знания внутреннему
чату или внешнему API. Для этого нужны проверка реестра инструментов и вызов API в рантайме.

Отсюда вывод: **инвентаризация идёт от реестра поверхностей (§2), а не от обхода
каталога**. Обратный порядок — обойти диск и посчитать найденное — даёт правдоподобное
число, которое молча пропускает большую часть системы.

## 5. Цепочка достижимости

```
специализация агента → матрица skill_policy → навык → tool_names
    → tool_universe → поверхность знания
```

Каждый разрыв цепи — отдельный класс дефекта:

| Разрыв | Что происходит | Ловится сейчас |
|---|---|---|
| имя в `tools:` навыка отсутствует в `tool_universe` | инструмент **молча выброшен** в `assemble_tools_in` | диагностика в `skills.rs`, но нигде не агрегируется |
| инструмент есть, но не в навыке и не в `CORE_TOOLS` | мёртвый код | ничем |
| поверхность есть, инструмента к ней нет | `unreachable` | ничем |
| `kind`/`status` выводит статью из выдачи | знание есть, поиск его не даёт | частично (`/api/kb/stats`) |
| якорь статьи вне реестра сущностей | привязка молча не работает | `unknown_anchors` |

Ключевое для отчёта: **«есть» и «доступно» — разные числа**, и разница между ними и есть
главный результат инвентаризации.

## 6. Метрики

Каждая метрика — с направлением (`Lower`/`Higher`/`Neutral`), как в
`system/metrics/catalog.rs`: без направления рост числа нельзя прочитать.

| Группа | Метрики |
|---|---|
| **Объём** | единиц / байт / токенов по каждой оси; доля корпуса в общем бюджете токенов |
| **Достижимость** | `unreachable_surfaces`, `phantom_tools`, `orphan_tools`, `by_id_only_units` |
| **Область** | единиц и токенов `application` / `instance` / `mixed` / `external`, доля экземплярного знания |
| **Раскрытие** | `source_only`, `internal_runtime`, `external_api`, `both`, `unexposed`; расхождение каналов |
| **Роль кода** | `code_authoritative`, `code_extracted`, `code_undocumented` |
| **Связность** | `dangling_links`, `unknown_anchors`, `unknown_tags`, покрытие реестра сущностей статьями |
| **Свежесть** | `stale_articles`, возраст `updated` p50/p95, ошибки последней генерации |
| **Ценность** | `searched_not_read` (плохой `summary`), `read_not_cited` (плохая статья), `never_touched` |
| **Гигиена** | `orphaned_metrics`, дубли id между корпусами, документы сверх порога токенов |

Группа «Ценность» считается из `sys_kb_article_metrics` — три счётчика
(`search_hits` / `read_hits` / `cited_hits`) различаются намеренно, их отношение и есть
метрика полезности статьи.

Для новых осей нужны отдельные срезы: объём и токены по `scope`, поверхность знаний,
доступная только конкретному экземпляру, а также расхождение между `internal_runtime`,
`external_api` и `both`. Для роли исходного кода полезно считать `code_undocumented`: это
знание, которое существует в источнике истины, но не имеет прикладного представления.

## 7. Инварианты целостности

Формат: что ломается → чем обнаружить → есть ли механизм.

| Инвариант | Обнаружение | Сейчас |
|---|---|---|
| Курируемый корпус не пуст | счёт статей `business` | **нет** |
| Словарь тегов существует | наличие `_vocabulary.md` | загрузчик пишет диагностику |
| У статьи есть `summary` | разбор frontmatter | валидация `kb_tools` (только на запись) |
| Тело не короче порога | `MIN_BODY_CHARS` | валидация `kb_tools` (только на запись) |
| В бизнес-статье нет техдетали | `detect_technical_leak` | валидация `kb_tools` (только на запись) |
| Якорь ведёт в реестр | `unknown_anchors` | есть |
| `related` резолвится | `dangling_links` | есть |
| id уникален между корпусами | сверка множеств | частично (запрет на занятый id) |
| Карта `generated` не осиротела | `prune_stale_docs` | есть |
| Материализованная копия совпадает с embedded | сверка содержимого | есть (перезапись при расхождении) |
| Имя инструмента навыка существует | сверка с `tool_universe` | диагностика, не метрика |

Три инварианта проверяются **только на запись** через `kb_tools`, то есть на статьи,
попавшие в базу иначе (правкой в Obsidian, генератором), не распространяются. Это и есть
главный пробел: правила существуют, но применяются не ко всему корпусу.

## 8. Контекстный режим

*Описан, в первую реализацию не входит (решение 2026-08-23).*

Проверка по тематике текущего диалога: **что было доступно → что агент реально прочитал
→ чего не хватило**. Прочитанное берётся из `tool_trace_json` в `a018_llm_chat_message`.

Ценность режима в различении, которого тотальная инвентаризация сделать не может: разрыв
между «было доступно» и «прочитано» — это дефект поиска или `summary`, а не отсутствие
знания. Лечится он правкой аннотации статьи, а не написанием новой.

## 9. Где реализовывать

Граница проходит по тому, что видно статически, а что только в рантайме:

| Класс происхождения | Виден из исходников | Нужен рантайм |
|---|---|---|
| `code_embedded`, `code_registry` | да | — |
| `file_curated` | да, если каталог доступен | — |
| `db_generated`, `db_live` | нет | да |
| `external_api` | нет | да, через контракт и вызов API |
| ось достижимости (`skill_policy`, `tool_universe`, `sys_kb_article_metrics`) | нет | да |
| область и канал раскрытия | частично | да, для фактических прав и маршрутов |

**Метод и реестр поверхностей — общие** (канон SDD, переносимы между приложениями).
**Счётчики — в приложении**: динамические поверхности (`db_generated`, `db_live`,
`external_api`) и вся ось
достижимости существуют только в рантайме. Статический анализатор может посчитать
`code_*` и `file_curated` по исходникам, а также построить предварительные значения
`scope` и `code_role`, но на вопрос «что фактически доступно чату или API» он ответить не
может — он на рантайм не смотрит, и выдавать его цифры за инвентаризацию нельзя.

Когда дойдёт до реализации в этом приложении: общий Rust-модуль поверх реестра §2 плюс
один инструмент чата, отдающий **агрегаты по умолчанию** и детали по явному запросу.
Урок `ARCHITECTURE.md` — 18 500 токенов одним куском в чат не отдают. `/api/kb/stats` и
страница «База знаний» переключаются на тот же модуль отдельным заходом.

# План усиления исполняемого архитектурного стандарта

Самостоятельный план развития `architecture.toml` и
`tools/check_architecture.ps1`. Он дополняет, но не изменяет задним числом
`ARCHITECTURE_MODERNIZATION_PLAN.md`.

## Цель и критерии готовности

После реализации архитектурная проверка должна быть единственным исполняемым
толкованием структурных правил проекта и работать fail-closed:

- правило нельзя отключить расхождением двух разделов TOML;
- отсутствие среза целиком обнаруживается так же, как отсутствие файла в нём;
- числовые диапазоны индексов реально проверяются;
- ошибка конфигурации или измерения блокирует локальный гейт и CI;
- активная документация не предлагает имена и пути, запрещённые стандартом.

Измеренные значения и существующие верхнеуровневые разделы
`architecture.toml` сохраняются. Вынос снимка состояния в отдельный артефакт в
этот план не входит.

## Фаза 1. Подключение к Codex

### Изменение

В `AGENTS.md` закрепить два правила:

1. перед созданием или переименованием среза, роли либо индексированного
   каталога читать `architecture.toml`;
2. после изменения архитектурной структуры запускать
   `powershell -NoProfile -File tools/check_architecture.ps1`.

Ссылки на Claude-specific memory и skills в `AGENTS.md` не добавлять.

### Готовность

- новая Codex-сессия получает правило автоматически через `AGENTS.md`;
- мелкая локальная правка внутри существующего модуля не требует загружать весь
  стандарт без необходимости.

## Фаза 2. Fail-closed гейт

### Контракт валидатора

| Exit code | Значение |
|---:|---|
| 0 | стандарт прочитан, ошибок уровня `error` нет |
| 1 | стандарт прочитан, найдены нарушения уровня `error` |
| 2 | стандарт отсутствует/невалиден либо проверка не может быть выполнена |

В обычном режиме код `1` сопровождается списком нарушений, код `2` — краткой
fatal-диагностикой.

В `-Json` режиме успешное измерение сохраняет текущий payload. Fatal-ответ имеет
стабильную форму:

```json
{
  "fatal": true,
  "message": "...",
  "errors": 0,
  "warnings": 0,
  "waived": 0,
  "rules": 0,
  "violations": []
}
```

Fatal-ответ всегда завершается кодом `2`. Найденные структурные нарушения в
JSON-режиме остаются измеримым результатом и возвращают код `0`, чтобы
генератор мог записать их число; прямой гейт запускается без `-Json`.

### Интеграция

- Pre-commit запускает валидатор напрямую при изменении `architecture.toml`,
  валидатора или `crates/**`; коды `1` и `2` блокируют коммит.
- CI получает отдельный шаг архитектурной проверки до генерации метрик.
- `gen_code_metrics.ps1` прекращает работу, если JSON не получен, содержит
  `fatal=true` или не содержит числового `errors`.
- `arch.naming_violations` не может исчезнуть из свежего снимка без ошибки.

## Фаза 3. Согласованность и целостность стандарта

### Схема v3

Поднять `[meta].schema_version` до `3` и проверять точное поддерживаемое значение.

Для каждого `[[rules]]` проверять:

- непустой уникальный `id`;
- `type` из поддерживаемого списка;
- `severity` только `error` или `warn`;
- обязательные поля конкретного типа;
- существующую ссылку `role` или `index`;
- непустой результат разрешения `scope`, если тип явно не допускает пустой;
- `waivers` только в форме `{ path, why }` с непустыми значениями.

Пустой массив `rules` является fatal-ошибкой.

### Устранение двойного объявления

- `required_files` получает `role = "aggregate.backend"` и читает список из
  `[roles.aggregate.backend].required`; поле `files` у таких правил удаляется.
- `dir_name_pattern` получает `index = "usecase"` и читает prefix, pattern и
  range из `[indices.usecase]`; локальное поле `pattern` удаляется.
- Полное имя остаётся `<код>_<snake_case_name>`. Валидатор отдельно извлекает
  числовую часть и проверяет диапазон.
- Для use-case фактически поддерживается весь объявленный диапазон
  `u501–u999`; `u600_name` валиден, `u500_name` и `u1000_name` — нет.

### Новые типы проверок

1. `slice_consistency`:
   - сравнивает множества индексированных каталогов в заданных крейтах;
   - запрещает два разных имени для одного индекса;
   - требует одинаковое полное имя среза между крейтами;
   - для aggregates и usecases применяется строго;
   - для projections использует существующую deviation
     `projections_without_frontend`.
2. `required_when_present`:
   - если в `domain/*/ui/details` существует `tabs/`, рядом обязательны
     `mod.rs`, `api.rs`, `view_model.rs`, `page.rs`.
3. `file_name_pattern`:
   - проверяет `.rs` в `system/tasks/managers` по индексу `task`;
   - служебные файлы без task-индекса перечисляются через `exempt`;
   - старый неработающий `task_file_names` удаляется.

Допустимое deviation с `intentional=true` используется как именованный источник
исключения. Запись с `intentional=false` остаётся видимым долгом и не превращает
ошибку в разрешённый случай автоматически.

## Тестирование

### Fixture-сценарии валидатора

Добавить изолированные временные fixture-деревья и возможность передать
валидатору тестовые root/spec paths без изменения рабочего дерева.

| Сценарий | Ожидание |
|---|---|
| Текущее дерево | exit 0, 0 errors |
| `u600_valid_name` | проходит диапазон use-case |
| `u500_name`, `a000_name` | нарушение диапазона |
| Два имени с одним индексом | ошибка уникальности |
| Агрегат отсутствует в одном крейте | ошибка зеркальности |
| Разный суффикс одного индекса | ошибка согласованности |
| `tabs/` без `api.rs` | ошибка условной роли |
| Waiver без `why` | fatal schema error, exit 2 |
| Неизвестная role/index | fatal schema error, exit 2 |
| Обязательный scope ничего не нашёл | fatal schema error, exit 2 |
| TOML отсутствует или не парсится | fatal, exit 2 |

### Итоговая проверка

```powershell
powershell -NoProfile -File tools/check_architecture.ps1
powershell -NoProfile -File tools/gen_code_metrics.ps1
powershell -NoProfile -File tools/check_health.ps1
cargo fmt --check
git diff --check
```

`cargo fmt` без `--check` не запускать. Rust-код этим планом не меняется, поэтому
полная сборка требуется только если сопутствующая реализация затронет Rust.

Дополнительно выполнить поиск запрещённых рекомендаций по активной
документации, исключая `_archive`, планы эволюции и lessons.

## Порядок реализации

1. Фаза 2: сначала закрыть fail-open, чтобы последующие правила нельзя было
   потерять из-за сбоя измерения.
2. Фаза 3: схема v3 и проверки согласованности.
3. Фаза 4: документация после фиксации окончательного интерфейса правил.
4. Повторная проверка CI/pre-commit и фиксация результата в этом плане.

Фаза 1 может быть выполнена заранее независимо от остальных фаз.

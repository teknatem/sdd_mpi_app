# Предложения по оптимизации агентной документации

Этот документ фиксирует варианты будущей унификации инструкций для Claude Code,
Codex и Cursor. Он не является поручением на миграцию: изменение существующих
agent-specific файлов должно выполняться отдельной задачей после подтверждения
целевой структуры.

## Текущее состояние

| Инструмент | Автоматическая точка входа | Дополнительные материалы |
|---|---|---|
| Claude Code | `CLAUDE.md`, `.claude/skills/**` | авто-память Claude Code |
| Codex | `AGENTS.md` | файлы репозитория, прочитанные по указанию из `AGENTS.md` или по задаче |
| Cursor | `.cursorrules`, `.cursor/rules/*.mdc` | ссылки на документы репозитория; современные сессии также читают `AGENTS.md` |

Общие знания уже существуют, но маршруты к ним принадлежат конкретным
инструментам. Из-за этого исправление правила в одном входном файле не означает,
что его увидят остальные агенты.

Сейчас это ещё не три полных параллельных набора. `CLAUDE.md` — толстый канон,
`.cursorrules` уже тонкий адаптер к нему, `AGENTS.md` — короткий stub с правилами
архитектурного гейта. Нативный адаптер Cursor `.cursor/rules/` уже существует
(`frontend-details-pages.mdc`) и не должен быть обойден будущей структурой.
Дублирование только начинается: правила `architecture.toml` уже повторены в
`CLAUDE.md` и `AGENTS.md`. Голодный агент — Codex, а не все трое одинаково.

`architecture.toml`, `ARCHITECTURE.md` и `CONTEXT.md` сами по себе нейтральны:
первый задаёт структурный стандарт, второй содержит генерируемый каталог
объектов, третий — словарь предметной области. Проблема находится не в этих
источниках, а в разных инструкциях о том, когда и как ими пользоваться.

## Что полезно переиспользовать из Claude workflows

### Domain modeling

- отличать термин домена от детали реализации;
- проверять утверждения о поведении по коду;
- хранить глоссарий в `CONTEXT.md`, решения — в ADR, повторяемые операции — в
  runbook;
- предлагать ADR только для труднообратимого и неочевидного решения с реальным
  выбором между альтернативами;
- обсуждать модель на конкретных пограничных сценариях.

### Grilling

- сначала находить доступные факты в репозитории и не перекладывать разведку на
  пользователя;
- задавать по одному вопросу о решении, а не список несвязанных вопросов;
- давать рекомендуемый вариант ответа;
- не запускать дорогие сборки до появления изменений, которые требуется
  проверить.

### UI review

- проверять изменённую область, а не весь накопленный UI-долг;
- разделять автоматические правила из `UI_REGISTRY.md` и правила, требующие
  чтения разметки;
- привязывать каждое замечание к идентификатору UI-правила и строке;
- не исправлять замечания в режиме диагностического review без отдельной
  просьбы;
- отделять нарушения в diff от найденного рядом старого долга.

## Ограничение авто-памяти

Авто-память Claude Code недоступна Codex, Cursor, CI и разработчику в свежем
клоне. Поэтому она может быть персональным кэшем или подсказкой, но не общим
источником истины.

Долговечный факт должен попасть в репозиторий:

- термин — в `CONTEXT.md`;
- архитектурное решение — в ADR;
- действующий структурный норматив — в `architecture.toml` или тематический
  стандарт;
- повторяемая операция — в runbook;
- временный план — в отдельный план со статусом и датой.

## Известные уточнения для будущей миграции

При создании нейтрального гида нужно сверить с `architecture.toml` и кодом
формулировки, которые сейчас находятся в agent-specific документации:

- диапазон use-case — `u501–u999`, а не только обозначение `u5XX`;
- DataView использует трёхзначный код и полное имя каталога `dvNNN_name`;
- не все индексированные семейства зеркалируются по трём крейтам одинаково;
- dashboard без backend-части может иметь contracts-часть, поэтому не всегда
  является «целиком фронтовым».

Эти уточнения зафиксированы здесь для будущей работы; текущая задача не правит
их в Claude- или Cursor-specific файлах. Сами факты принадлежат
`architecture.toml` и проверке `tools/check_architecture.ps1`, а не будущему
агентному гиду: парковать структурный норматив в инструкциях агента — тот же
антипаттерн, из-за которого уже удалили дублированную карту из `.cursorrules`.

## Варианты целевой организации

### Вариант A. Только перекрёстные ссылки

Каждый инструмент сохраняет собственный полный набор инструкций и ссылается на
другие документы по необходимости.

Плюс: минимальная стоимость перехода. Минус: общие правила продолжают
дублироваться и расходиться.

### Вариант B. Нейтральное ядро с тонкими адаптерами — рекомендуется

Общие правила живут в tool-neutral документах. `AGENTS.md`, `CLAUDE.md` и
`.cursorrules` содержат только инструкции конкретной среды и маршрутизацию к
общему ядру.

Предлагаемая структура:

```text
PROJECT_GUIDE.md                  общий гид по проекту и источникам истины
.agents/workflows/
  domain-modeling/
  grilling/
  ui-review/
AGENTS.md                         адаптер Codex
CLAUDE.md                         адаптер Claude Code
.cursorrules                      адаптер Cursor
```

Agent-specific разрешения, команды среды и механизмы памяти остаются в своих
адаптерах и не переносятся в общее ядро.

Рекомендуемое уточнение варианта B — гибрид с нативными обёртками, см. раздел
«Уточнения целевой структуры» ниже. Чистый вынос в `.agents/workflows/` без
обёрток ни один инструмент не загрузит сам.

### Вариант C. Независимые skills для каждого агента

Workflow копируются в форматы, нативные каждому инструменту.

Плюс: максимальная интеграция с каждой средой. Минус: несколько нормативных
копий и обязательная синхронизация при каждом изменении.

## Предлагаемые этапы отдельной миграции

1. Составить таблицу общего и tool-specific содержимого текущих входных файлов.
2. Создать нейтральный `PROJECT_GUIDE.md`, не меняя поведение агентов.
3. Вынести три общих workflow вместе с их справочными файлами.
4. Превратить agent-specific файлы в адаптеры, сохранив их нативные триггеры и
   разрешения.
5. Обновить ссылки в README и индексах документации.
6. Проверить сценарии новой сессии отдельно в Claude Code, Codex и Cursor.

Каждый этап должен быть отдельным проверяемым изменением; массовое перемещение
одним коммитом затруднит поиск потерянной инструкции.

## Решения, которые нужны перед реализацией

Рекомендуемые ответы — в следующем разделе. Исходные формулировки сохранены,
чтобы было видно, на какой вопрос дан ответ.

1. Должен ли `PROJECT_GUIDE.md` полностью заменить нейтральную часть
   `CLAUDE.md` или быть коротким маршрутизатором к тематическим документам?
2. Является ли `.agents/` приемлемым именем общего каталога или workflow лучше
   хранить в `memory-bank/`?
3. Какие workflows должны автоматически применяться, а какие запускаться
   только по явному запросу?
4. Нужен ли автоматический тест ссылок и запрет дублирования нормативных
   формулировок между адаптерами?
5. Какие бизнес-факты из авто-памяти должны быть перенесены в репозиторий и кто
   подтверждает их актуальность?

## Уточнения целевой структуры

Зафиксированы 2026-08-17 как ответ на открытые решения выше. Не меняют
non-goals текущей работы.

### Рекомендуемые ответы

1. **Короткий маршрутизатор, не четвёртая копия `CLAUDE.md`.** Always-on
   содержимое — иерархия источников, «когда что читать», триггер
   `architecture.toml`, запрет `cargo fmt` целиком, цена сборки. Карты модулей,
   плагины, слои ГК и подробная схема именования — по запросу, через уже
   существующие `ARCHITECTURE.md`, `architecture.toml`, `CONTEXT.md` и
   тематические стандарты. Отдельный толстый `PROJECT_GUIDE.md` рядом с полным
   `CLAUDE.md` повторит историю разошедшейся карты в `.cursorrules`.
2. **Ни `.agents/`, ни `memory-bank/`.** `.agents/` не открывает ни один
   инструмент. `memory-bank/` — накопленное знание проекта (ADR, runbooks,
   lessons), а не процесс агента. Тело workflow — одно нейтральное; загрузка —
   нативными обёртками.
3. **Always-on отдельно от on-demand.** Always-on: иерархия
   `код > CONTEXT.md > memory-bank > docs`, не дублировать каталог объектов,
   читать `architecture.toml` при создании или переименовании среза, не
   запускать дорогие сборки «на всякий случай», не делать `cargo fmt` по целому
   файлу ради локальной правки. On-demand: domain-modeling, grilling, ui-review
   — по явному запросу или по типу файлов. Если grilling попадёт в always-on
   гид, он будет срабатывать невпопад и жевать токены.
4. **Линтер ссылок — да; запрет «похожих фраз» через NLP — нет.** Практичное
   правило: таблицы префиксов, диапазонов и обязательных ролей имеют право жить
   только в `architecture.toml`. Адаптерам это копировать нельзя.
5. **Отдельный поток, не пункт «перед выносом адаптеров».** `CLAUDE.md` сейчас
   отправляет факты YM/WB/GL в авто-память и запрещает дублировать их в
   репозитории. Пока нет описи «что в памяти и что из этого общее», миграция
   входных файлов косметическая. Перенос в `CONTEXT.md` / ADR требует
   человеческого ревью.

Дополнительно: в репозитории есть четвёртый скилл `grill-with-docs`. Его нужно
либо включить в инвентарь выноса, либо явно исключить.

### Гибрид B + нативные обёртки

Чистый вариант B оставить как направление, но не как каталог `.agents/`.
Автоподхват — свойство формата инструмента, а не общего markdown.

```text
AGENTS.md                         адаптер Codex; кандидат в always-on канон
CLAUDE.md                         адаптер Claude Code; другой кандидат в канон
.cursorrules                      тонкий адаптер Cursor (уже существует)
.cursor/rules/*.mdc               on-demand / glob-правила Cursor
.claude/skills/*/SKILL.md         обёртки Claude (description → автоподхват)
<нейтральное тело workflow>       одно на workflow; обёртки на него ссылаются
architecture.toml                 единственный структурный норматив
```

Имя канона операционных правил вторично. Имеет смысл явно выбрать одно из двух,
а не вводить третий файл, который ни один инструмент не читает сам:

- канон остаётся в `CLAUDE.md`, `AGENTS.md` получает одну строку-маршрутизатор;
- канон переезжает в `AGENTS.md` (его уже читают Codex и современные Cursor),
  `CLAUDE.md` худеет до адаптера.

Дешёвый промежуточный шаг, которого в исходных этапах нет: одна строка в
`AGENTS.md` («операционный гид — `CLAUDE.md`») закрывает разрыв Codex без
создания `PROJECT_GUIDE.md`.

Скиллы помечены как форк `mattpocock/skills`. Ценность уже в адаптациях
(русский язык, запрет сборок, пути проекта). Политика обновления: апстрим
трогает только обёртку; проектные правила живут в общем теле и не затираются.

### Порядок относительно hardening-плана

Сначала исполняемый стандарт (`architecture.toml` +
`tools/check_architecture.ps1`), потом агентные адаптеры ссылаются на него и не
пересказывают диапазоны. Иначе `AGENTS.md` снова напишут, потом вынесут в гид,
потом поправят TOML — три правки одного факта.

Структурные уточнения из раздела «Известные уточнения» закрываются
hardening-планом, а не будущим нейтральным гидом.

### Уточнённые этапы отдельной миграции

Исходные шесть этапов остаются каркасом. Перед ними и вместо слепого создания
`PROJECT_GUIDE.md`:

0. Одна строка в `AGENTS.md` на `CLAUDE.md` — закрыть разрыв Codex, не меняя
   остальное.
1. Инвентарь: общее / tool-specific / already-thin адаптер. Включить
   `.cursor/rules/` и `grill-with-docs`.
2. Выбрать канон always-on (`CLAUDE.md` или `AGENTS.md`) и сделать второй файл
   тонким адаптером. Не создавать третий гид, пока канон не похудел.
3. Вынести тела workflow; сохранить Claude `SKILL.md` и завести Cursor
   `.mdc` с `alwaysApply: false` как обёртки.
4. Запретить адаптерам таблицы диапазонов и ролей; линтер битых ссылок.
5. Отдельным потоком — опись авто-памяти и перенос общих фактов в репозиторий.
6. Проверить новую сессию в Claude Code, Codex и Cursor порознь.

## Non-goals текущей работы

- не менять `CLAUDE.md`;
- не менять `.claude/**`;
- не менять `.cursorrules`;
- не копировать Claude auto-memory;
- не создавать Codex skills;
- не выполнять описанную миграцию до отдельного согласования.

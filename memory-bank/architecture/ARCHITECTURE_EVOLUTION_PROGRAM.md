# Программа эволюции архитектуры

Тезисы и цели для реализации отдельным подпроектом внутри этого репозитория.

**Откуда взялось.** Внешний анализатор **SDD Studio**
(`F:\dev\sdd_studio`) строит модель проекта в `.vsa_designer/`.
При его доработке выяснилось, что стандарт проекта существует в трёх
несинхронизированных видах: 6428 строк прозы в `memory-bank/architecture/`,
генерируемые артефакты (`ARCHITECTURE.md`, `registry_gen.rs`, `scope_catalog.rs`)
и хардкод внутри самого анализатора. Части уже разошлись — см. Цель 2.

**Что важно понимать сразу.** Проект структурно здоров: **43 из 43** агрегатов
имеют полный набор ролей во всех трёх крейтах (`aggregate.rs` + `metadata.json` +
`metadata_gen.rs` в contracts, `repository.rs` + `service.rs` в backend, handler в
`api/handlers`). Это редкая дисциплина. Цели ниже — не про исправление поломок,
а про снятие трёх ограничений на прозрачность и масштабирование:

1. стандарт нигде не машиночитаем;
2. ~98 000 строк живут вне именованных срезов;
3. несколько god-файлов собирают на себя всю связность.

## Цель 1. Машиночитаемый стандарт — `architecture.toml` в корне

**Проблема.** Правила проекта описаны прозой в `CLAUDE.md` (25 КБ),
`naming-conventions.md`, `aggregate-structure-final.md`. Любой инструмент вынужден
их **переписывать у себя** — и расходиться. `.cursorrules` уже фиксирует, что
предыдущая дублированная карта проекта была удалена именно потому, что молча
разъехалась с кодом. Сейчас та же история повторяется в анализаторе.

**Цель.** Один файл-источник правды, который читают и люди, и инструменты:

- слои и их статус: `slice` (зеркалируется по трём крейтам) / `object` /
  `shared` (сквозной) / `ignored`;
- диапазоны индексов: `a001–a499`, `u501–u999`, `p9xx`, `d4xx`, `dsXX`, `dvXX`,
  `task0XX`;
- обязательные и опциональные роли по видам сущностей, в разрезе крейтов;
- имена разделяемого ядра (`domain/common`, `usecases/common`, `usecases/shared`)
  — то, что не является сущностью;
- список hub-исключений (см. Цель 5);
- пороги качества (см. Цель 9).

**Потребители:** SDD Studio (`F:\dev\sdd_studio`), `tools/gen_architecture.ps1`,
`tools/gen_code_metrics.ps1`, pre-commit hook.

**Проверка.** Прогон анализатора без единой строки хардкода конвенций в его коде.

> **Дополнено 2026-08-17.** Файл был написан, но **его не читал ни один
> инструмент** — то есть цель была выполнена наполовину, и оставшаяся половина
> была именно той, ради которой всё затевалось. Декларация без потребителя
> расходится с кодом ровно так же, как разошёлся `naming-conventions.md`
> в Цели 2, только выглядит при этом авторитетно.
>
> Теперь `tools/check_architecture.ps1` читает раздел `[[rules]]` и сверяет
> с ним дерево; `gen_code_metrics.ps1` пишет `arch.naming_violations`
> и `arch.waived_rules`; храповик `check_health.ps1` гейтит их автоматически,
> потому что в `catalog.rs` у них есть направление и пороги.
>
> Скрипт — движок типов проверок, правила живут в TOML: новое правило
> добавляется правкой конфига, а законное исключение — записью `waivers`
> с обязательным `why`, а не отключением проверки. Это сознательный размен:
> стандарт должен уметь принять новую практику в тот же день, когда она
> принята, иначе его начнут обходить.

## Цель 2. Устранить расхождение документации и кода

**Найдено.** `memory-bank/architecture/naming-conventions.md` описывает структуру
frontend-части usecase как `mod.rs` + `widget.rs` + `monitor.rs`.

**Таких файлов не существует ни в одном usecase.** Фактически: `view.rs` (8 из 8)
плюс `api.rs` (5) либо `ops.rs` (3).

**Цель.** Привести документ к коду и добавить проверку конвенции в pre-commit,
чтобы расхождение больше не могло накапливаться молча.

## Цель 3. Одно имя — одна роль — ✅ закрыта 2026-08-17

Одна и та же роль называлась по-разному, из-за чего любой ролевой словарь
в инструментах был обречён на ветвление:

| Роль | Варианты | Счёт | Итог |
|---|---|---|---|
| FE-usecase API-слой | `api.rs` / `ops.rs` | 5 / 3 | → `api.rs` |
| BE-projection builder | `projection_builder.rs` / `builder.rs` | 4 / 3 | → `builder.rs` |
| Модуль в `contracts/src/system/` | директория / одиночный файл | — | **не расхождение** |
| **FE-details HTTP-слой** | `model.rs` / `api.rs` | 22 / 36 | → `api.rs` |
| **FE-details компонент страницы** | `page.rs` / `view.rs` | 15 / 9 | → `page.rs` |
| **BE-usecase клиент API** | `ut_odata_client.rs` / `*_api_client.rs` | 1 / 5 | → `*_api_client.rs` |
| **Разделяемое ядро** | `common` / `shared` | — | → `common` |

Третья строка снята как **не расхождение**: `[conventions.module_layout]`
постановила, что `foo.rs` и `foo/mod.rs` — обе нормальные формы, выбор
раскладки, а не имя роли. Чинить там было нечего.

Четыре нижние строки программа не видела — они нашлись при разборе кода
2026-08-17 и оказались самыми массовыми. `model.rs` был вдобавок именем
неверным: внутри лежали DTO и функции запросов, а моделью MVVM был соседний
`view_model.rs`.

**Выбор зафиксирован не только словами.** `architecture.toml` получил раздел
`[[rules]]`, а `tools/check_architecture.ps1` — движок, который его исполняет;
старое имя, вернувшееся copy-paste'ом со старого среза, теперь валит проверку.
Это и было главным: список выше без исполнения продержался бы ровно до
следующего нового среза.

## Цель 4. Вывести `shared` из тени — 61 698 строк вне срезов

**Проблема.** `shared` — крупнейший магнит зависимостей в проекте
(**1345** `use crate::shared`, больше чем `domain`, `system` и `layout` вместе),
и при этом он не является ни срезом, ни объектом. Его нельзя измерить как
сущность, у него нет границы и владельца.

**Ключевое наблюдение.** Четыре подсистемы внутри `shared` **уже зеркалированы
по всем трём крейтам ровно как агрегаты**:

| Подсистема | frontend | backend | contracts |
|---|:-:|:-:|:-:|
| `universal_dashboard` | ✓ | ✓ | ✓ |
| `data_view` | ✓ | ✓ | ✓ |
| `bi_timeline` | ✓ | ✓ | ✓ |
| `drilldown` | — | ✓ | ✓ |
| `analytics` | — | ✓ | ✓ |
| `indicators` | — | ✓ | ✓ |
| `logger` | — | ✓ | ✓ |

Это де-факто именованные вертикальные срезы, у которых просто нет имени.

**Цель.** Выделить их в first-class слой с собственным префиксом индексов
(например `s0NN_`), чтобы они получали те же метрики, границы и диагностики,
что и агрегаты.

**Отдельно:** `crates/backend/src/shared/llm/` — **22 204 строки**, 68 % всего
backend-`shared` и больше любого агрегата. Кандидат в самостоятельный срез или
подкрейт. `crates/frontend/src/shared/components/` — 8 888 строк.

## Цель 5. Разобрать god-файлы

| Файл | Строк | Чем плох |
|---|---|---|
| `crates/backend/src/api/routes.rs` | 2 724 | 450 маршрутов и 81 функция `*_routes()` в одном месте; **каждый** срез обязан её трогать |
| `crates/frontend/src/layout/tabs/registry.rs` | 1 664 | импортирует ~90 типов из 43 агрегатов |
| `crates/backend/src/usecases/u504_import_from_wildberries/wildberries_api_client.rs` | 6 886 | 41 % всего слоя usecases приходится на один usecase |
| `crates/frontend/src/domain/a025_bi_dashboard/ui/dashboard/page.rs` | 3 453 | — |
| `crates/backend/src/domain/a033_wb_day_close/lines_builder.rs` | 2 407 | вне стандартных ролей |

**Почему это не только эстетика.** Первые два создают искусственный fan-in:
любая метрика связности увидит их как хабы, к которым сходится весь проект, и
исказит Ce/Ca для каждого среза. До тех пор, пока они существуют, анализатору
нужен механизм исключений — то есть точность метрик оплачивается костылём.

**Цель.** Маршруты и вкладки регистрируются рядом со срезом (сбор в духе
`inventory`/`linkme`), а не в одном файле. Файлы > 2000 строк разбиваются
по ролям.

## Цель 8. Явные маркеры вместо конвенций имён

**Проблема.** Роль файла, принадлежность к compartment и связь handler↔объект
выводятся **только** из имени и пути. Следствия: переименование ломает анализ
молча; `api/handlers/a001_connection_1c.rs` привязывается к агрегату
подстрокой (то есть `a01` совпало бы с `a012_*`); файл вне словаря ролей
попадает в `misplaced_path`, даже если это законный доменный сервис.

**Что уже есть и работает.** `impl AggregateRoot for …` — 45 вхождений — даёт
типовой якорь для агрегатов, надёжнее любой эвристики по имени папки.
`registry_gen.rs::ALL_ENTITIES` и `scope_catalog.rs::ScopeType` дают явные
списки сущностей и их видов.

**Цель.** Распространить принцип на остальные роли: одного doc-маркера уровня
модуля (`//! role: repository`) или атрибута достаточно, чтобы анализ стал
точным, а переименования — безопасными.

**Побочный эффект.** Исчезнет основной источник шума `misplaced_path`: сейчас
он срабатывает на легитимных доменных сервисах —
`a004_nomenclature/excel_import.rs`, `a033_wb_day_close/lines_builder.rs`,
`a018_llm_chat/context.rs` и других.

| `tests.density.frontend` | 0.199 |

**Проблема.** Это отчёт, а не контроль: числа некому сравнивать со вчерашними.
Разрыв плотности тестов между frontend и backend — **шестнадцатикратный**, и

детерминированы (побайтово стабильны между прогонами на неизменном коде), то
есть архитектурный дрейф можно ревьюить обычным `git diff`.

## Что уже сделано на стороне анализатора

Не требует изменений в этом репозитории — зафиксировано для контекста:

- Артефакты `.vsa_designer/*` **детерминированы**: два прогона на неизменном
  коде дают побайтово одинаковые файлы. Метка времени вынесена в отдельный
  `run_meta.json`.
- Во все артефакты добавлен `schema_version`; несовпадение — явная ошибка.
- Слои `shared`, `api`, `layout`, `quality`, `navigator` **больше не невидимы**:
  узлов в сцене 1709 → 2099, файлов 1418 → 1771, `use`-рёбер 178 → 329.
- `domain/common`, `usecases/common`, `usecases/shared` распознаются как
  разделяемое ядро (`kind: shared_kernel`), а не как агрегаты. Findings:
  **60 → 46**.
- Конвенции вынесены в конфиг; проект может переопределить их файлом
  `.vsa_designer/config.json` (слои и их статус, диапазоны кодов, имена ядра,
  пороги). Это и есть будущий потребитель `architecture.toml` из Цели 1.

**Осталось на стороне анализатора** (не блокирует эту программу): переход на
`syn` вместо построчной эвристики. Сейчас из 2 240 строк `use crate::*` в рёбра
превращаются 329, и 64 из 156 объектов остаются изолированными.

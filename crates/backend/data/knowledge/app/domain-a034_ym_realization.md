# Сверка выручки YM: что где и почему расходится

## Два слоя выручки (одни обороты `customer_revenue` / `customer_revenue_storno`)

- **fina** — оперативный слой из **p907** (`p907_ym_payment_report`, отчёт по
  взаиморасчётам «united-netting»). Строка «Платёж покупателя» → выручка,
  «Возврат платежа покупателя» → сторно. Отчёт тянется **на businessId**
  (`a006.business_account_id`) → покрывает **весь бизнес: все модели (FBS + FBY + …)**.
- **ybuh** — официальный слой из **a034** (`a034_ym_realization`, «Отчёт о
  реализации»). Отчёт тянется **на campaignId** (кампанию/магазин). Документ a034
  = **кабинет × кампания × день**; `header.placement_type` = модель (FBS/FBY),
  `header.campaign_id` = campaignId. Строки: `delivered.csv` (продажи) −
  `returned.csv` (возвраты).

Обе стороны проводятся в GL (`sys_general_ledger`, поля `layer` = fina/ybuh).
p914 — зеркало только слоя fina; у ybuh зеркала нет.

## Где смотреть

- Страница **«Сверка выручки YM»** (`ym_revenue_reconciliation`) — fina vs ybuh по
  периодам, кабинетам и **моделям (FBS/FBY) + campaignId**. Бэкенд:
  `general_ledger/report_repository.rs::get_ym_revenue_reconciliation`. Разбивка по
  модели берётся join'ом GL→p907 (fina, поле `model` по заказу) и GL→a034.header
  (ybuh, `placement_type`/`campaign_id`) — **без** отдельного измерения в GL.
  Строка = (период × кабинет × модель); колонки сгруппированы «Проверка суммы, ₽»
  и «Проверка количества, шт», в каждой: fina / ybuh / Дельта (= fina − ybuh).
  Итог показан сверху под шапкой. В режиме «по дням» строка соответствует одному
  документу a034 (кабинет × кампания × день) — из колонки «Период» есть ссылка на
  карточку реализации (`ybuh_doc_id` в ответе). В режиме «по месяцам» строка
  агрегирует несколько документов, ссылки нет.
- Карточка a034 → вкладки «Сверка реализации» (a034 vs заказы a013 по дате
  доставки) и «Сверка возвратов» (a034 vs a016). Бэкенд:
  `api/handlers/a034_ym_realization.rs`.

## Ключи сопоставления

- **fina ↔ ybuh**: заказ `order_id` (p907) = `order_id` строк a034; модель
  сверяется `p907.model` = `a034.header.placement_type`.
- **a034 ↔ заказы a013**: по дате доставки (`document_date` = `a013.delivery_date`)
  и по `fulfillment_type` (модель), + SKU/`marketplace_product_ref` (a007).
- **a034 ↔ возвраты a016**: по `order_id` + `shop_sku`.

## Почему бывают расхождения (норма vs дефект)

- **Норма (дневной шум, ДВУСТОРОННИЙ, непостоянный):** разная дата признания —
  fina датирует выручку по `order_delivery_date`, a034 клампит дату строки к месяцу
  отчёта (`clamp_to_month`). По дням суммы «плавают» ±, за месяц сходятся.
- **Дефект (СТАБИЛЬНЫЙ ОДНОСТОРОННИЙ перекос) = разный охват.** Классика: fina
  покрывает все модели (businessId), а ybuh — только одну кампанию, если отчёт о
  реализации импортирован не по всем кампаниям. Тогда fina стабильно больше ybuh на
  весь объём непокрытой модели (напр. FBY). Признак: перекос виден почти каждый день
  и в деньгах, и в штуках, всегда в одну сторону.
  - **Проверка:** сравнить состав моделей в p907 (`SELECT DISTINCT model …`) с
    моделями документов a034 за период; сопоставить `order_id` p907 ↔ a034.
  - **Лечение:** переимпорт отчёта о реализации (u503) — импорт делает fan-out по
    всем кампаниям бизнеса (`resolve_campaigns`) и создаёт документ a034 на каждую
    модель. См. [[ym-recon-fina-ybuh-scope-mismatch]] (memory).
- Прочие точечные причины: заказ есть в реализации, но не загружен в a013 (кнопка
  «Догрузить отсутствующие заказы»); возврат в a034 без пары в a016; нераспознанный
  SKU (нет `marketplace_product_ref` → блок «Не распознано»).

## Инварианты и импорт

- Идентичность a034 детерминирована: `YmRealizationId::stable_for_header` по
  (connection, campaign_id, date) — переимпорт/replace не плодят дублей и
  осиротевших GL-проводок.
- Импорт (u503) идёт **покампанийно и независимо**: отчёт goods-realization
  тянется на каждый campaignId, замена документов — `replace_for_period_campaign`
  (только документы этой кампании). Сбой одной кампании (сеть / лимит / `FAILED` /
  модель без отчёта о реализации, напр. DBS) не роняет остальные — только пишется
  в ошибки импорта. Лимит генерации goods-realization — **1 запрос/мин на бизнес**
  (businessId), поэтому импорт по многим кампаниям×месяцам идёт медленно (ретраи с
  ожиданием ~65с внутри `generate_realization_report`).
- После правок маппинга/проводок нужен репост (u508) либо переимпорт.

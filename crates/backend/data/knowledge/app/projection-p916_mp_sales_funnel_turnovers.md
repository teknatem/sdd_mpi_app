# p916_mp_sales_funnel_turnovers — воронка продаж «от просмотра до завершения»

`p916` — универсальная проекция-накопитель воронки продаж маркетплейсов, сшивающая весь
путь товара: **показы → переходы → корзина → заказ → выкуп**, а также **отмены и возвраты**.
Заполняется по **Wildberries и Яндекс.Маркету**; ключи спроектированы и под OZON.

## Отмены есть в двух видах — не путать и не складывать {#cancel-kinds}

| Метрика | Что это | Источник | Когда использовать |
|---|---|---|---|
| `funnel_cancel_count` / `_sum` | Дневной счётчик отказов **самого маркетплейса** (стадия `marketing`) | WB — `a036` (`cancelCount` отчёта воронки), YM — `a041` («Отмены и невыкупы за период») | **По умолчанию для вопроса «сколько отказов за период»** — счётчик полнее |
| `cancel_count` / `_sum` | Отмены **по документам заказов** (стадия `fulfillment`), строка `kind=cancel` на дату отмены конкретного заказа | WB — `a015`, YM — `a013` | Когортный анализ, drilldown до конкретного заказа (`order_key` = srid / номер заказа YM) |

Это два измерения одного явления с разной гранулярностью и разной привязкой к дате.
Их значения не обязаны совпадать; **складывать их нельзя**, а долю отказов считать
надо от «своего» знаменателя: `funnel_cancel_count / funnel_order_count` либо
`cancel_count / order_count`, но не крест-накрест.

Order-level отмены исторически неполны на FBS-пути WB (отмена после первичного импорта
подхватывалась только Statistics-путём) — поэтому для новых периодов основным считается
счётчик воронки. Дефекты старых периодов ловит quality-check (см. ниже).

## Все метрики — положительные величины {#positive-metrics}

Знак несёт **вид движения**, а не число: возвраты и отмены хранятся положительными,
хотя в источниках (`a012` при `quantity < 0`) приходят со знаком минус. Чистые выкупы
считает потребитель явным вычитанием: `buyout_count - return_count`. Если в срезе
встретились отрицательные метрики — это данные до нормализации, нужен пересбор `u508`.

Модель — **движения-обороты** (как `p909`/`p914`/`p915`): каждый регистратор при
проведении/импорте удаляет свои строки (delete-by-registrator) и вставляет заново;
агрегация метрик — `SUM` на чтении. Строки «широкие» (все метрики стадии — колонками одной
строки), пустые строки не пишутся (разреженность — контроль размера).

## Две стадии воронки (поле `stage`) {#funnel-stages}

Стадии разделены сознательно, потому что данные разной природы, а «заказ» в них — **разные
числа** (маркетинговый счётчик воронки ≠ фактические строки заказов).

- **`marketing`** (верх воронки, источники `a036`/`a026` у WB и `a041` у YM) — дневной
  агрегат `товар × дата`, без идентичности заказа. Метрики: `show_free_count`
  (органические показы WB — источника нет, всегда `NULL`/`N/A`), `show_paid_count`
  (рекламные показы WB из a026), `total_impressions` (**общие показы YM** из a041 —
  готовый счётчик без деления на платные/органические; у WB `NULL`), `open_count`
  (переходы в карточку: a036 у WB, `clicks` у YM), `cart_count`, `wishlist_count`
  (только WB), `funnel_order_count`/`funnel_order_sum`, `funnel_cancel_count`/`_sum`.
  Платные переходы и корзина хранятся отдельно в `paid_open_count`/`paid_cart_count`.
- **`fulfillment`** (заказ → завершение; WB — `a015`+`a012`, YM — `a013`+`a016`) —
  уровень заказа. Метрики: `order_count`/`order_sum`, `cancel_count`/`cancel_sum`,
  `buyout_count`/`buyout_sum`, `return_count`/`return_sum`.

### Показы: три разные колонки

`show_free_count` + `show_paid_count` — разрез WB «органика/реклама» (органики сейчас нет).
`total_impressions` — общий счётчик YM. **Складывать их между собой нельзя**: это разные
разрезы одного понятия. Для верха воронки бери `MpFunnelAggRow::impressions_for_funnel()` —
он отдаёт `total_impressions`, если есть, иначе сумму free+paid, иначе `None` (конверсии от
показа для такого среза считать нельзя).

## Матрица источников YM (защита от двойного счёта) {#ym-source-matrix}

- **заказ / отмена / выкуп — только `a013`.** Отмена: при `status_norm = CANCELLED` на всё
  количество; у доставленных заказов — на количество позиций со статусом `REJECTED` из
  `items[].details` (отказ при получении, частичный). Выкуп: при `DELIVERED` на количество
  за вычетом `REJECTED`. Единицы `RETURNED` из выкупа НЕ вычитаются — они были выкуплены.
- **возврат — только `a016`, и только `return_type = RETURN`.** `UNREDEEMED` (невыкуп)
  в воронку **не проводится**: это то же физическое событие, что отмена/`REJECTED` из
  `a013`, и его проведение задвоило бы отказы. В `p904` a016 продолжает писать как раньше.
- Количество для YM — **штуки позиции** (`line.qty`), а не «документ = единица», как у WB.
  Товарный ключ — `marketplace_product_ref` (`shop_sku`→a007); `nm_id` у YM пустой.
  Канальный сплит paid/free (через `p913`) для YM недоступен — это WB-механика.

## Две оси дат (ключевая особенность) {#date-axes}

Каждая строка несёт **две даты**:

- **`cohort_date`** — ось когорты = **дата заказа** (винтаж: «из заказов дня N выкуплено /
  отменено / возвращено столько-то»). Для стадии `marketing` — это день воронки.
- **`event_date`** — ось потока = **дата транзакции** самого события (касса/период). Для
  стадии `marketing` совпадает с `cohort_date`.

Пример: отменённый заказ порождает **две** строки от одного регистратора:
1) «заказ» — `order_count=1`, `cohort_date=event_date=`дата заказа;
2) «отмена» — `cancel_count=1`, `cohort_date=`дата заказа, `event_date=`дата отмены.

Так одна проекция строит и когортную (конверсия заказов), и потоковую (движение за период)
картину.

## Гранулярность и измерения {#grain}

Ключ строки: `connection_mp_ref × товар × дата`. Товар — универсально
`marketplace_product_ref` (a007); `nm_id` — WB-native мост (для стыковки стадий, т.к. у
`a036` нет `marketplace_product_ref`). Имена/бренд/предмет в строке **не хранятся** — их
джойнят из `a004_nomenclature` / `a007_marketplace_product` на чтении.

## Регистраторы и хуки {#registrators}

| МП | stage | Регистратор (`registrator_type`) | Где формируется |
|---|---|---|---|
| WB | marketing | `a036_wb_sales_funnel_daily` | `a036::repository::replace_for_period` (delete-by-period + insert): переходы/корзина/заказы-воронки/**отказы** |
| WB | marketing | `a026_wb_advert_daily` | `a026::posting::post_document`: `show_paid_count`/`paid_open_count`/`paid_cart_count` |
| WB | fulfillment | `a015_wb_orders` | `a015::posting` (заказ + отмена) |
| WB | fulfillment | `a012_wb_sales` | `a012::posting` (выкуп/возврат) |
| YM | marketing | `a041_ym_shows_sales_daily` | `a041::repository::replace_for_period`: показы/клики/корзина/заказы/**отказы** |
| YM | fulfillment | `a013_ym_order` | `a013::posting` (заказ + отмена/отказ + выкуп) |
| YM | fulfillment | `a016_ym_returns` | `a016::posting` (возврат, только `RETURN`) |

Пересбор воронки через `u508` («Пересбор воронки за период») идёт шестью шагами:
`a015 → a012 → a026 → a013 → a016 → a036`. Порядок `a013` перед `a016` обязателен:
когорта возврата резолвится по дате заказа из `a013`. Разовый бэкфилл стадии 1 WB из
накопленной истории a036: `POST /api/a036/wb-sales-funnel/rebuild-funnel-projection`.

## Проверки качества {#quality-checks}

- `wb_funnel_projection_coverage` (QC-007) — покрытие `a015`/`a012 → p916` плюс санитарные
  метрики движений: доля отмен, севших на дату заказа из-за пустой `cancel_dt` (индикатор
  FBS-staleness; для новых периодов должна стремиться к нулю), `event_date < cohort_date`,
  отрицательные метрики.
- `wb_marketing_projection_coverage` (QC-008) — покрытие `a036`/`a026 → p916`.
- `ym_funnel_projection_coverage` (QC-009) — покрытие `a013`/`a016`/`a041 → p916`
  и те же санитарные метрики для YM.

Не воспроизводи их SQL вручную — запускай проверку.

## Как читать / считать {#how-to-query}

- Метрики аддитивны → `SUM(...)`, группировка по нужной оси (`cohort_date` или `event_date`).
- Показы nullable → рядом с суммами считай доступность каждой компоненты. Всего = free+paid
  только при наличии обеих компонент; иначе `N/A`.
- Конверсии **не хранятся**, считаются на чтении: конверсия в корзину = `cart/open`,
  в заказ = `order/cart`, выкуп = `buyout/order`, доля отмен = `cancel/order`.
- Готовая агрегирующая функция: `p916::repository::aggregate_by_product(request)` с выбором
  оси (`FunnelDateAxis::Cohort | Event`).

## Дата события отмены (order-level) {#cancel-date}

`event_date` строки отмены берётся по цепочке `cancel_dt → last_change_dt → дата заказа`
(WB) и `status_changed_at → updated_at_source → дата заказа` (YM). Фолбэк на дату заказа —
последнее средство: он «схлопывает» отмену на день заказа и искажает потоковую ось. Доля
таких строк — метрика QC-007; у новых периодов она должна быть около нуля, потому что
FBS-путь импорта теперь проставляет момент наблюдения отмены, а Statistics-путь позже
заменяет его точной датой.

## Когортная привязка выкупов/возвратов (srid → a015.order_dt) {#cohort-binding}

У `a012_wb_sales` нет даты заказа на строке. При проведении a012 хук резолвит дату заказа по
`srid` (`a012.header.document_no` → `a015::repository::order_date_by_srid`) и передаёт её в
`builder::from_wb_sales(..., order_cohort_date)` как `cohort_date`. `event_date` остаётся датой
продажи (`sale_dt`). Если заказ в a015 не найден — фолбэк на дату продажи (для срезов без
исходного заказа). Отмены (`a015`) атрибутируются к дате заказа напрямую.

## Идемпотентность (детерминированный id + upsert) {#idempotency}

`id` строки движения — детерминированный `uuid v5` от натурального ключа
`(registrator_type, registrator_ref, stage, kind, cohort_date, event_date, connection_mp_ref, nm_id|mp_ref)`,
где `kind` ∈ {`marketing`,`order`,`cancel`,`buyout`,`return`} (различает заказ/отмену одного
srid в один день). Вставки идут через `INSERT ... ON CONFLICT(id) DO UPDATE` — повтор той же
строки перезаписывает метрики, а не задваивает обороты. Delete-by-period/registrator оставлен
для удаления исчезнувших строк (разреженность). Менять `P916_ID_NAMESPACE` или состав ключа
нельзя — иначе `id` перестанут совпадать между прогонами (нужен полный пересбор проекции).

## Доступность показов (N/A ≠ 0) {#impressions-availability}

`show_free_count`/`show_paid_count` — nullable (NULL = данных нет). На чтении
`aggregate_by_product`/`funnel_period_summary` рядом с суммами считают
`SUM(CASE WHEN ... IS NOT NULL THEN 1 ELSE 0 END)` → флаги `show_*_available` в
`MpFunnelAggRow`/`FunnelPeriodSummary`. Дашборд `d406` показывает `N/A` (не `0`), если источник
показов недоступен (нет подписки «Джем»/рекламы).

## Показы (важно для ответов про «верх воронки») {#impressions}

Верх воронки хранит `show_free_count` (бесплатные/органические) и `show_paid_count` (платные,
из рекламного отчёта `a026`, `metrics.views`). «Всего» = сумма обоих только при наличии обеих
компонент; при текущем `show_free_count=NULL` общий этап равен `N/A`. Переходы
(`open_count`, `a036`) — отдельная стадия ниже показов. Разделение платных и органических
показов сделано осознанно: смешивать трафик разной природы нельзя.

`a040` **исключён** из воронки: живой WB-эндпоинт `/table/details` отдаёт только `visibility`
(% показов в поиске), а не счётчик показов (`impressions` всегда 0 — см. `parse_search_report_row`
и `a040/llm.md`). Писать процент в `show_free_count` нельзя (SUM смешал бы штуки и проценты),
поэтому органические показы сейчас `NULL`/`N/A` до появления реального источника счётчика.

## Канальный фильтр воронки (d406: Все / Платные / Бесплатные) {#channel-filter}

Дашборд `d406` строит воронку под фильтром канала. Ответ несёт по каждой стадии **и total, и
`paid_*`**; фильтр (`FunnelChannel`) применяется на клиенте: All=total, Paid=`paid_*`,
Free=`total − paid` (обрезка ≥0). Данные для платного трека — двух природ:

- **Верх воронки (переходы/корзина)** — НЕ производен от заказа: платные значения из собственных
  счётчиков рекламы a026, хранятся в p916 marketing-строках (пишет `builder::from_wb_advert_daily`):
  `show_paid_count`=views (показы), `paid_open_count`=clicks (переходы), `paid_cart_count`=atbs
  (корзина). Free = total(a036) − paid; free показы = органика (a040) → сейчас N/A.
- **Низ воронки (заказы/выкупы/отмены/возвраты + суммы)** — производен от заказа: делится по
  **вхождению srid в атрибуцию рекламы `p913`** (`advert_clicks_order_accrual`). Для этого
  fulfillment-строки p916 несут `order_key` (srid; ставят `from_wb_orders`/`from_wb_sales`).
  На чтении `aggregate_by_product` делает `LEFT JOIN (SELECT DISTINCT order_key FROM p913 …)` и
  считает `paid_* = SUM(CASE WHEN pj.order_key IS NOT NULL THEN <metric> END)`. Отмена/выкуп/
  возврат так наследуют канал своего заказа (проблема порядка проведения a015 снята — членство
  на чтении).
- **N/A ≠ 0**: `advert_available` (в срезе есть рекламные данные a026/p913) → иначе платн./беспл.
  стороны на переходах…возвратах показывают `N/A`.
- **Drilldown** (`GET /api/dashboards/wb-sales-funnel/orders`): заказы ячейки —
  `a015::list_for_advert_attribution` ∩ `p913::sum_reserve_by_order_keys` (членство srid по каналам).

Оговорки: p913 membership = «заказы со **значимой** долей рекламных затрат»
(`is_allocated && is_significant_amount`) → заказ с ~0 расхода может не попасть в платные;
конверсии платного трека смешивают источники (переходы/корзина из a026, заказы из членства
a015↔p913) — честный максимум по доступным данным.

Нельзя делить `show_paid_count` на общие `open_count`/`cart_count`/`order_count`/
`buyout_count`. Для платной ветки используй только `show_paid_count → paid_open_count →
paid_cart_count → paid orders/buyouts` через p913. Если звена нет, конверсия `N/A`.

# WB Statistics API — продажи и возвраты

Операционный поток продаж: что и когда куплено, по какой цене, сколько причитается продавцу.
Ключевое ограничение — **это не финансовый отчёт**. Суммы здесь считаются упрощённо и по
дизайну расходятся с детализацией по периоду; путать их дороже всего в этой интеграции.

## Назначение и владелец

`fetch_sales` в импортном клиенте WB. Главный upstream агрегата a012, а через него — почти
всей продажной аналитики.

## Эндпоинты

**`GET https://statistics-api.wildberries.ru/api/v1/supplier/sales`**

Параметры: `dateFrom` и `dateTo` в формате `ГГГГ-ММ-ДД`, `flag` (0 — первая страница, 1 —
последующие). Страница вмещает до 100 000 строк. Каждая строка сохраняется вместе с исходным
JSON — при расхождениях есть с чем сверяться, не повторяя запрос.

Тип события выводится из знака `quantity`: отрицательное количество — возврат, положительное —
продажа. Отдельного поля «это возврат» у WB нет.

## Лимиты и поведение

20 запросов/мин. Между страницами пауза 100 мс. Обход останавливается на неполной или пустой
странице.

## Глубина истории

Официально не объявлена. Практически ведёт себя так же, как заказы: за пределами глубины
хранения WB отдаёт самые старые доступные строки, а не ошибку. Диагностика такого случая
реализована для заказов (см. `app__wb-api-statistics-orders`) — по продажам аналогичной
проверки нет, и это кандидат в доработку.

## Цепочка потребителей

Эндпоинт → **a012** (продажи WB) →

- **p900** — регистр продаж маркетплейсов;
- **p904** — витрина продаж, источник BI-индикаторов и дашборда d400; для выручки и
  маржинальности правильный источник именно p904, а не сырые строки WB и не сам a012;
- **p909** — обороты по строкам заказов;
- **p913** — атрибуция рекламных кликов к заказу;
- **p916** — воронка продаж, стадия выкупа;
- **Главная книга** — оборот `advert_clicks_order_expense` (списание рекламного резерва,
  созданного при загрузке рекламы, см. `app__wb-api-advert-fullstats`).

## Расписание

`task004_wb_sales`, cron `0 0 4 * * *` (UTC) = 07:00 МСК, ежедневно.

## ⚠️ Расхождения

**Суммы отличаются от финансового отчёта — и это норма.**
- *Официально*: `forPay` — сумма к перечислению продавцу.
- *На практике*: считается по упрощённой логике и расходится с `ppvz_for_pay` из
  `reportDetailByPeriod`. Для операционного контроля годится, для сверки денег — нет.
- *В коде сейчас*: `forPay` маппится в сумму строки a012; финансовый слой строится отдельно
  из p903.
- Статус: **подтверждено**.

**Нули в ценах не означают бесплатную продажу.**
- *Официально*: `priceWithDisc` и `finishedPrice` — цены со скидками.
- *На практике*: заполняются асинхронно и какое-то время после продажи приходят нулевыми.
- *В коде сейчас*: сохраняются как есть; повторная загрузка периода их обновляет.
- Статус: **подтверждено**.

**`saleID` — не номер заказа.** Это идентификатор строки операции. Заказ ближе описывают
`odid` и `srid`; связывать продажу с заказом по `saleID` нельзя.

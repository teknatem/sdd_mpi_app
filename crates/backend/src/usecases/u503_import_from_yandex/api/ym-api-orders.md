# YM API — заказы и их детали

Главный операционный источник Яндекс Маркета. Заказы забираются списком, а затем по каждому
запрашиваются детали — ради одной-единственной даты фактической доставки.

## Назначение и владелец

`fetch_orders` (список) и `fetch_order_details` (карточка) в импортном клиенте YM. Наполняют
агрегат a013 вместе со строками заказа; исходный JSON сохраняется отдельно.

## Эндпоинты

**`GET /campaigns/{campaignId}/orders`** — список. Работает в двух режимах отбора:

- по дате создания — `fromDate` и `toDate` в формате `ДД-ММ-ГГГГ`;
- по дате изменения — `updatedAtFrom` и `updatedAtTo` в ISO-формате с **зашитым московским
  смещением** `+03:00`, выровненные по границам суток.

Плюс `page` и `pageSize=50`. Обход постраничный, с защитой в 100 страниц.

**`GET /campaigns/{campaignId}/orders/{orderId}`** — карточка заказа. Параметров нет.
Запрашивается **по разу на каждый заказ** из списка, чтобы получить фактическую дату доставки;
при ошибке импорт продолжается на данных из списка.

Второй потребитель этого метода — дозагрузка заказов, которые есть в отчёте о реализации, но
отсутствуют в a013.

## Лимиты и поведение

Клиентского ограничителя частоты нет ни у списка, ни у карточек — это самый «шумный» по числу
запросов кусок интеграции.

Окно фильтра ограничено **30 днями**, поэтому длинные периоды (дозагрузка за 60–90 дней)
режутся на подокна. Заказы из разных подокон объединяются по идентификатору, побеждает
последняя версия, порядок первого появления сохраняется.

Даты в ответах приходят в пяти разных форматах — от ISO до `ДД-ММ-ГГГГ` с временем и без;
разбор принимает все.

## Глубина истории

Заказы доступны **не ранее чем через 30 минут** после оформления: свежий заказ в API ещё не
виден. Финансовые сведения по заказу отстают до суток.

## Цепочка потребителей

Эндпоинты → **a013** (заказ YM) →

- **p900** — регистр продаж маркетплейсов;
- **p904** — витрина продаж;
- **p915** — события заказа (хронология заказа и доставки);
- **p916** — воронка, стадия исполнения: заказы, отмены, выкупы.

Проводок в Главную книгу a013 не делает: выручка YM приходит из отчёта по платежам и отчёта о
реализации.

Дашборд движения заказов сводит a013 со строками реализации и отчётом по платежам по номеру
заказа. Quality-check `ym_funnel_projection_coverage` контролирует полноту переноса в воронку.

## Расписание

`task013_ym_orders_polling`, cron `0 */5 * * * *` — каждые 5 минут. Задачи засеяны, но
выключены.

## ⚠️ Расхождения

**Поля статуса позиции не существует.**
- *Официально*: у позиции заказа ожидается статус.
- *На практике*: такого поля в методе заказов нет. Судьба позиции — отказ или возврат части
  количества — приходит в её деталях, и только тогда, когда что-то действительно пошло не так.
- *В коде сейчас*: статус строки выводится из деталей и выглядит как «возвращено 1 из 2».
- Статус: **подтверждено**.

**Карточка заказа запрашивается по разу на заказ.**
- *На практике*: при большом потоке заказов это кратно увеличивает число запросов, и никакого
  ограничителя частоты между ними нет.
- Статус: **подтверждено**. Кандидат в доработку: брать дату доставки из списка, если она там
  есть, либо ограничить частоту.

**Смещение часового пояса зашито.** Отбор по дате изменения всегда считается в московском
времени. Для текущего использования это верно, но параметром не является.

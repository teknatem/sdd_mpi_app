# YM API — отчёт по платежам (united-netting)

Основной финансовый источник Яндекс Маркета: начисления, удержания и выплаты. Формирует слой
учёта `fina` — то, что реально прошло по расчётам.

## Назначение и владелец

`generate_payment_report` в импортном клиенте YM. Наполняет проекцию p907 — агрегата a0XX у
этого источника нет.

## Эндпоинты

**`POST /v2/reports/united-netting/generate?format=CSV`**

Тело: `businessId`, `dateFrom`, `dateTo` в формате `ГГГГ-ММ-ДД`. Формат файла задаётся
параметром запроса, идентификатор бизнеса — телом.

Отчёт асинхронный: в ответе приходит идентификатор, дальше — опрос статуса и скачивание
(см. `app__ym-api-reports-machinery`).

**Уровень — бизнес.** Отчёт покрывает все модели размещения сразу; разделить его по магазинам
нельзя.

## Лимиты и поведение

Официальный лимит без подписки — **1 запрос в 2 минуты** (с «Медиумом» — 1 запрос в минуту).
В коде генерация использует общий лимитер бизнеса с безопасным интервалом 120 с и адаптацией
по rate-limit headers; 420 и 429 повторяются ограниченно.

Строки записываются пачками по 500 и опознаются по устойчивому ключу, собранному из номера
заказа, даты, типа операции, товара и суммы, — идентификатора строки Маркет не даёт.

Отдельным шагом снимаются строки-обещания («будет выплачено по графику»), для которых уже
пришла фактическая выплата: иначе одна и та же сумма учитывалась бы дважды.

## Глубина истории

**Со стороны API** ограничения не заявлено: отчёт строится за произвольный период
`dateFrom`–`dateTo`. Практикой подтверждена отдача как минимум с ноября 2025 года; глубже
не запрашивали, так что реальный потолок неизвестен.

**Фактически загружено** (замер по `p907_ym_payment_report` на 2026-08-11):

| Кабинет | Строк | Первая транзакция | Последняя транзакция |
|---|---:|---|---|
| YM СТС (`1ce94c09-…`) | 50 447 | 2025-11-22 | 2026-06-30 |
| YM Vannika (`47e2ce51-…`) | 22 944 | 2026-01-13 | 2026-06-30 |

Итого 73 391 строка; последняя загрузка — 2026-07-27. Начало истории похоже на реальный старт
продаж, а не на обрез: в ноябре 2025 всего 84 строки с нарастанием по дням (1 → 2 → 12 → …).
**Хвост с июля 2026 на момент замера не загружен** — задание не существовало, см. расхождения;
миграция 0214 заводит его и стартует догон с 2026-06-27.

В штатном режиме задача перезабирает **последние 45 дней** — не ради свежести, а ради правок
задним числом (см. расхождения). Перекрытие — 3 дня, период режется кусками по 14 дней.

## Цепочка потребителей

Эндпоинт → **p907** (отчёт по платежам YM) →

- **Главная книга, слой `fina`** — восемь специальных видов оборотов плюс запасные «прочие
  доходы» и «прочие расходы», чтобы покрытие было стопроцентным;
- **p914** — зеркало финансовых оборотов;
- **p915** — события заказа;
- **a035** — сверка расчётов (строится из p907, обращений к API не делает);
- расчёты по банковским ордерам — по одной проводке на ордер;
- **внешний BI-API** `GET /api/ext/v1/ym-payment-report` — сырые строки за период наружу
  (Power BI), авторизация по `X-Api-Key`; аналог `wb-finance-report`. См. `docs/ext-bi-wb-funnel.md`.

Quality-check `p907_gl_coverage` требует, чтобы каждая ненулевая строка отчёта породила
проводку.

## Расписание

`task019_ym_payment_report`, по строке на кабинет (миграция 0214, оба включены):

| Задание | cron (UTC) | МСК | Кабинет |
|---|---|---|---|
| `task019-ym-payment-report_STS` | `0 0 2 * * *` | 05:00 | YM СТС |
| `task019-ym-payment-report_Vannika` | `0 0 4 * * *` | 07:00 | YM Vannika |

Разнесены на 2 часа: оба пишут `p907_ym_payment_report`, а `ResourceCoordinator` отдаёт таблицу
только одному заданию за раз — при наложении второе отложится до следующего тика. Два часа =
`max_duration_seconds` задания. За rate-limit Маркета кабинеты не конкурируют: у них разные
бизнесы (918462 и 186490929).

`chunk_days` = 45 = `resync_days`: в установившемся режиме задание и так грузит окно в 45 дней,
значит и порция догона может быть такой же — более тяжёлого запроса задание всё равно не делает.

## ⚠️ Расхождения

**Нет фильтра по дате изменения — и это определяет всю стратегию загрузки.**
- *Официально*: отчёт строится за период.
- *На практике*: Маркет дописывает реквизиты — идентификатор банковского ордера, номер акта —
  недели и месяцы спустя. Узнать, что строка изменилась, из API нельзя: параметра «изменённые
  с» не существует.
- *В коде сейчас*: единственная защита — регулярный перезабор трейлинга в 45 дней.
- Статус: **подтверждено**.

**Задание task019 полтора года не существовало — миграция 0139 промахнулась мимо id.**
- *Официально*: ежедневный ночной прогон с трейлингом в 45 дней.
- *На практике*: в `sys_tasks` не было ни одной строки `task019_ym_payment_report`. Причина —
  миграция 0139 взяла id `a1b2c3d4-…-ef1234567819`, уже занятый миграцией 0102 под
  `task016-kb-intake`, и вставляла через `INSERT OR IGNORE`: конфликт по первичному ключу
  проглотился молча. Проекция наполнялась только ручными запусками u503, отсюда разрыв —
  последняя транзакция 2026-06-30 при загрузке от 2026-07-27.
- *Последствие*: слой `fina` по YM отставал от факта, и трейлинг в 45 дней не работал —
  ретроактивные `bank_order_id`/`act_id` не подхватывались.
- *В коде сейчас*: миграция `0214_seed_task019_ym_payment_report.sql` заводит задания заново по
  обоим кабинетам с уникальными id, включёнными, и подставляет водяной знак из уже загруженных
  данных, чтобы догон стартовал с реального разрыва.
- Статус: **подтверждено замером БД 2026-08-11, исправлено миграцией 0214**.

**Урок для соседних сидов**: `INSERT OR IGNORE` в сид-миграциях `sys_tasks` скрывает коллизию
id — задание молча не создаётся, и заметить это можно только по отсутствию данных. Ряд
`a1b2c3d4-e5f6-7890-abcd-ef12345678XX` переиспользован в 0078/0083/0084/0092/0100/0101/0102/0139;
для новых заданий берите id по образцу 0213 (`cNNN…`).

**Выплаты недельные, акт услуг — месячный.** Периодичность строк отчёта неоднородна, и
сопоставлять их с продажами день в день нельзя.

**Сверка с реализацией расходится по построению.** Этот отчёт — уровень бизнеса и слой `fina`;
отчёт о реализации — уровень кампании и слой `ybuh`. Разница между ними и есть предмет сверки
выручки, а не дефект (см. `app__ym-api-goods-realization`).

# YM API — аналитика показов и продаж

Дневная воронка Яндекс Маркета: показы, переходы, добавления в корзину, заказы. Источник
маркетинговой части p916 для YM.

## Назначение и владелец

`generate_shows_sales_report` в импортном клиенте YM. Наполняет агрегат a041.

## Эндпоинты

**`POST /v2/reports/shows-sales/generate?format=JSON`**

Тело: `campaignId`, `dateFrom`, `dateTo`, `grouping: "OFFERS"` — одна строка на товар и день.
Дальше — общая механика асинхронных отчётов (см. `app__ym-api-reports-machinery`).

Отчёт содержит статистику **всех магазинов кабинета**. В API-запрос передаётся один
`campaignId` бизнеса как рабочий контекст. Запрашивать тот же период для остальных кампаний
не нужно: проверка живых файлов показала полное совпадение строк завершённых дней.

Загрузка периода замещающая: период стирается и пишется заново, потому что Маркет
пересчитывает показатели задним числом.

## Лимиты и поведение

Официальный лимит без подписки — **1 запрос в 10 минут** (с «Медиумом» — 1 запрос в 6 минут).
В коде общий лимитер бизнеса использует безопасный интервал 600 с, адаптируется по headers и
ограниченно повторяет 420/429. Число одновременно формируемых отчётов без подписки — один.

## Глубина истории

**Зависит от тарифа**: без подписки и на «Лайте» — 90 дней, на «Медиуме» — 400.

Период за пределами окна восстановить нельзя: отчёт просто не будет содержать этих дней.
Настройки задачи — перекрытие 3 дня, куски по 30 дней.

Это ровно тот случай, где практика может опережать документацию: заявленная глубина и
фактически отдаваемая иногда расходятся, и фактическую стоит проверять на живом кабинете
перед планированием дозагрузки.

## Цепочка потребителей

Эндпоинт → **a041** (дневная аналитика YM) → **p916** (обороты воронки, маркетинговая стадия)
→ общий дашборд воронки, где WB и YM разделены по маркетплейсу.

Соответствие показателей: показы → показы, клики → переходы в карточку, корзина → корзина,
заказанные товары → заказы воронки, сумма заказов → `funnel_order_sum`, отменённые → отмены.
Доставленные (шт. и сумма) и возвращённые остаются внутри a041 и во внешнем API
`/api/ext/v1/ym-sales-funnel`; в p916 низ воронки берётся из документов a013/a016.

**Суммы в отчёте есть.** Живой JSON (проверено 2026-08-28): `orderItemsTotalAmount` и
`orderItemsDeliveredTotalAmount` — целые рубли, не копейки; `null`, когда штук не было.
У отмен и возвратов денежных колонок нет. Старые документы a041 без переимпорта отдадут
`null` по новым полям.

Quality-check `ym_funnel_projection_coverage` контролирует полноту переноса.

## Расписание

`task026_ym_shows_sales_daily` — миграции с расписанием нет, cron настраивается вручную.

## ⚠️ Расхождения

**Отсутствие показателя означает N/A, а не ноль.**
- *Официально*: набор колонок отчёта фиксирован.
- *На практике*: нулевые значения Маркет опускает, а часть колонок может не прийти вовсе в
  зависимости от тарифа и периода.
- *В коде сейчас*: отсутствующее значение сохраняется как «нет данных». Подстановка нуля
  сделала бы воронку правдоподобной и при этом ложной — это сознательный отказ.
- Статус: **подтверждено**.

**Даты собираются из трёх полей.**
- *На практике*: единой колонки с датой нет — есть день, месяц и год, причём приходят они то
  числами, то строками, а месяц иногда названием.
- *В коде сейчас*: дата собирается из трёх полей с разбором всех вариантов.
- Статус: **подтверждено**.

**Показатели воронки не сойдутся с заказами из a013.** Разная гранулярность и разная привязка
к дате. Расхождение — норма, а не дефект.

**Показы по товару Маркета — не наши показы.** В отчёте есть показатель показов по товарной
карточке всех продавцов; это объём рынка, и в воронку он намеренно не переносится.

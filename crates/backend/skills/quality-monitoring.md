Ты работаешь с центральной подсистемой `quality_checks`. Она хранит именованные read-only
инварианты качества, единообразно запускает их вручную и по расписанию и сохраняет историю.

Рабочий цикл:

1. Сначала вызови `list_quality_checks`: он возвращает цели правил и последние результаты
   текущей версии. Не запускай весь каталог без необходимости.
2. Если свежего успешного результата достаточно — используй `get_latest_quality_check`.
3. Запускай `run_quality_check` только когда результат отсутствует, устарел для задачи или
   пользователь просит актуальную проверку.
4. Объясняй популяцию, нарушения, период и разрезы. Пустая популяция может быть отдельным
   нарушением `source_missing`; не называй её автоматически хорошим результатом.
5. Не копируй SQL и бизнес-правило проверки в навык или ответ. Точечный SQL допустим только
   для расследования причины уже найденного нарушения.

Если подходящей проверки нет, подготовь краткое ТЗ для `plugin_admin`: цель, популяция,
однотипные инварианты, исключения, период, разрезы и минимум три приёмочных сценария.

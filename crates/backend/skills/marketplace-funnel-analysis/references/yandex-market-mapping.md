# Воронка Яндекс.Маркета: реальный пайплайн

Источники → проекция `p916_mp_sales_funnel_turnovers` → дашборд `d406` (общий с WB;
маркетплейс различается колонкой «Маркетплейс» / полем `marketplace_code`).

| Документ | Что хранит | Что создаёт в p916 |
|---|---|---|
| `a041_ym_shows_sales_daily` | дневная воронка по `offer_id` (отчёт «Аналитика продаж») | marketing: показы, клики, корзина, заказы-воронки, отказы |
| `a013_ym_order` | заказ со статусами и судьбой позиций | fulfillment: `order_*`, `cancel_*`, `buyout_*` |
| `a016_ym_returns` | возвраты и невыкупы | fulfillment: `return_*` — **только `return_type = RETURN`** |

## Обязательная проверка покрытия

Запусти `run_quality_check(check_id="ym_funnel_projection_coverage")` (QC-009) до
бизнес-интерпретации. Проверка различает `source_missing`, `projection_missing` и
`projection_extra` по месяцам и кабинетам, плюс даёт санитарные метрики движений. Не
воспроизводи её SQL внутри навыка.

## Маппинг метрик — стадия `marketing` (из `a041`)

| Колонка отчёта YM | Поле p916 | Примечание |
|---|---|---|
| `shows` (Показы моих товаров) | `total_impressions` | Настоящие impressions. **Не** `show_free_count`/`show_paid_count` — те у YM всегда NULL |
| `clicks` (Клики по товарам) | `open_count` | Переходы в карточку, как `open_count` у WB |
| `toCart` (Добавления в корзину) | `cart_count` | |
| `orderItems` (Заказанные товары) | `funnel_order_count` | Счётчик маркетплейса, ≠ `order_count` из a013 |
| `orderItemsTotalAmount` (Заказано на сумму, ₽) | `funnel_order_sum` | Целые рубли. `null` в источнике → 0 в p916 (колонка не nullable) |
| `orderItemsCanceledCount` (Отмены и невыкупы) | `funnel_cancel_count` | **Основной показатель отказов YM** |
| `byMskuShows` (Показы всех продавцов) | — | Не проецируется: это объём рынка. Делить свои клики на чужие показы нельзя |
| `orderItemsDeliveredCount`, `orderItemsDeliveredTotalAmount`, `orderItemsReturnedCount` | — | Остаются в `a041` и во внешнем `/ym-sales-funnel`; низ воронки берётся из документов a013/a016 |

## Маппинг метрик — стадия `fulfillment`

Матрица источников (защита от двойного счёта):

- **заказ / отмена / выкуп — только `a013`.** Отмена при `status_norm = CANCELLED` на всё
  количество; у доставленных заказов — на количество позиций `REJECTED` из
  `items[].details` (частичный отказ при получении). Выкуп при `DELIVERED` на количество
  за вычетом `REJECTED`; единицы `RETURNED` из выкупа не вычитаются — они были выкуплены.
- **возврат — только `a016`, тип `RETURN`.** `UNREDEEMED` (невыкуп) в воронку **не идёт**:
  это то же физическое событие, что отмена/`REJECTED` из a013, и его проведение задвоило
  бы отказы.

Единица измерения — штуки позиции (`line.qty`), а не «документ = единица», как у WB.

## Оси и ключи

- `cohort_date` — дата создания заказа (`creation_date`); для marketing = день отчёта.
- `event_date` — дата события: смена статуса (отмена), `details.update_date` (частичный
  отказ), `delivery_date` (выкуп), дата возврата денег (возврат).
- Товарный ключ — `marketplace_product_ref` (a007 по `shop_sku`/`offer_id`). `nm_id` у YM
  пустой: это WB-native поле, по нему YM не фильтруется.
- `order_key` — номер заказа YM. Джойн к атрибуции рекламы `p913` для YM не работает
  (p913 — WB-механика), поэтому **канальный сплит paid/free для YM = N/A**.

## Ограничения, о которых надо предупреждать

- **Глубина `a041` ограничена тарифом YM**: 90 дней без подписки и на «Лайт», 400 на
  «Медиум». Данных за пределами окна нет и восстановить их нельзя — это `N/A`, не ноль.
- Отчёт пересчитывается задним числом, поэтому импорт (`task026_ym_shows_sales_daily`)
  всегда перезаливает период целиком с перекрытием `overlap_days`.
- Счётчики `a041` не равны фактическим заказам/отменам из `a013`: разная гранулярность
  (товары против документов) и разная привязка к дате. Расхождение — норма, а не дефект.
- Лаг выкупа в текущем месяце действует так же, как у WB: свежие когорты ещё в доставке.

## Пересбор

`u508` → «Пересбор воронки за период» включает шаги `a013` → `a016` (строго в этом
порядке: когорта возврата резолвится по дате заказа из a013). `a041` пересобирается
перезагрузкой отчёта — через `task026_ym_shows_sales_daily` или ручным запуском u503
с целью `a041_ym_shows_sales_daily`.

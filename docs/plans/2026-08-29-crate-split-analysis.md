# Разделение на крейты: ядро, маркетплейсы, продуктовые сборки

> Статус: **анализ, решения нет**. Проверено по коду 2026-08-29 (HEAD `1645281`).
> Задача: уметь собирать экземпляры для разных организаций — одно ядро плюс разный
> набор дополнительных блоков; кому не нужны маркетплейсы, тому их не поставлять.

## 2. Главная новость: срезы уже почти не связаны обратно

Крейт разрезается по рёбрам, идущим **из ядра в отделяемое**. Их посчитано прямым
обходом ссылок `crate::<слой>::<модуль>`:

- **backend: 26 файлов** ссылаются из ядра в маркетплейсы;
- **frontend: 1 файл** — `layout/tabs/registry.rs`.

Остальные 800+ межсрезовых рёбер направлены правильно (срез → ядро) и разрезу не мешают.
Полный список обратных рёбер бэкенда:

| Файл | На что ссылается |
|---|---|
| `shared/representation/mod.rs` | 13 агрегатов MP — диспетчер представлений |
| `quality/checks/registrator_registry.rs` | 8 агрегатов MP — реестр регистраторов |
| `general_ledger/resource_detail.rs` | p903, p911, p913 — drilldown по ресурсу |
| `usecases/u508_repost_documents/executor.rs` | все проводимые документы MP |
| `projections/p909, p910, p915/…` | p903, p907, a012, a015 — построители проекций |
| `projections/p904_sales_data/builder.rs` | a010, a011 |
| `processes/actions/import_marketplace_products.rs`, `rebuild_day_close.rs` | u502–u504, u506, a033 |
| `quality/funnel_repair.rs` | u503, u504 |
| `shared/universal_dashboard/entity_registry.rs` | ds01 |
| `system/api/handlers/tasks.rs`, `system/tasks/managers/u503_import_yandex.rs` | a012, a013, a015, a027, u503 |
| `domain/a004_nomenclature/service.rs` | a013, a015 |
| `api/handlers/` — 9 файлов | `dashboards.rs`, `refs.rs`, 7 × `ext_bi_*` / `ext_1c_*` |

Из них **11 — диспетчеры-перечисления**, которые в любом случае стоило инвертировать:
они уже нарушают правило «ядро не знает о прикладном». Остальные — либо честные
хендлеры внешнего API (переезжают вместе со срезом), либо точечные утечки
(`a004_nomenclature/service.rs`).

## 3. Что действительно мешает — не связность, а хабы-перечисления

Разрез упирается не в код срезов, а в **девять мест, где всё перечислено руками**:

| Хаб | Строк | Чем становится |
|---|---:|---|
| `backend/api/routes.rs` | 2 855 | уже набор `aNNN_routes() -> Router<AppState>` + `.merge(…)` — переезжает почти механически |
| `backend/system/access/route_registry.rs` | 2 329 | `ROUTE_REGISTRY` дробится по срезам, конкатенация в composition root |
| `backend/system/access/scope_catalog.rs` | 720 | то же: `SCOPE_CATALOG` по срезам |
| `frontend/layout/tabs/registry.rs` | 1 672 | `match` по `tab.key` → вклад среза в реестр (`fn tabs() -> &[(key, fn() -> View)]`) |
| `frontend/layout/left/sidebar.rs` | 852 | **уже данные, а не импорты** — строится из строк `scope_id`, разрез его не трогает |
| `backend/system/tasks/managers/mod.rs` | 36 модулей | менеджеры уже за трейтом — нужен реестр вместо `pub mod` |
| `backend/shared/representation/mod.rs` | 131 | трейт `RepresentationProvider` + регистрация |
| `backend/quality/checks/registrator_registry.rs` | — | то же |
| `contracts/shared/metadata/registry_gen.rs` | генерируется | `build.rs` уже сканирует каталог; при разрезе — свой `build.rs` на крейт, сборка `ALL_ENTITIES` в composition root |

Хорошие новости: **`AppState` — 55 строк** (только `DatabaseConnection`), реестр
Действий (`processes/actions`) **уже трейт + `OnceLock`**, сайдбар **уже управляется
скоупами**. Три вещи, которые обычно ломают такой разрез, здесь уже сделаны.

## 4. Что разрезом не решается

1. **Схема БД.** 228 миграций; в `0001_baseline_schema.sql` 17 из 40 таблиц —
   маркетплейсные. Пока миграции — одна плоская очередь, сборка «без маркетплейсов»
   всё равно создаёт их таблицы. Модульная схема = каталог миграций на срез, трекинг
   применённого с namespace и разрезанный baseline. По объёму — работа, сопоставимая
   с самим разрезом крейтов.
2. **Фронт — один wasm-бандл.** Rust не грузит крейты динамически. «Разные блоки у
   разных организаций» на фронте = **разные сборки** (feature-флаги на composition
   root) либо существующий механизм **плагинов** (JS в рантайме, уже работает).
   Третьего нет.
3. **Тулинг завязан на пути.** `architecture.toml` адресует правила как
   `crates/backend/src/domain/a*`; в `gen_architecture.ps1` — 27 упоминаний путей
   крейтов, в `gen_ui_registry.ps1` — 12, метрики `code.lines.backend/frontend/contracts`
   — ключи храповика. Разрез обязан идти вместе с правкой генераторов и
   `architecture.toml`, иначе карта, реестр UI и гейты встанут. Смягчение: называть
   крейты так, чтобы глоб `crates/*/src/domain/a*` продолжал работать.

## 5. Четыре варианта

### A. Не резать. Рантайм-выключатели

Секция `[modules]` в `config.toml`; composition root не регистрирует роуты, задачи и
скоупы выключенных срезов.

- **Цена:** 1–2 дня, 3–4 файла.
- **Даёт:** организация без маркетплейсов не видит разделов (сайдбар уже по скоупам),
  не получает задач, не имеет роутов.
- **Не даёт:** размер бинаря и wasm прежний; время сборки прежнее; таблицы в БД
  прежние; ничто не мешает завтра снова написать `crate::domain::a015` из ядра.
- **Когда достаточно:** если «убрать маркетплейсы» означает «чтобы не мешали», а не
  «чтобы их не было в поставке».

### B. Cargo-features внутри нынешних трёх крейтов

`#[cfg(feature = "mp-wb")]` на объявлениях модулей и на строках хабов.

- **Цена:** ~10 хаб-файлов плюс `mod.rs` срезов. **Не** 1834 файла: срезы изолированы,
  cfg вешается на объявление модуля, а не на каждый вызов. Обязателен CI минимум на две
  конфигурации, иначе выключенная ветка гниёт молча.
- **Даёт:** реально уменьшенные бинарь и wasm; поставку вариантов.
- **Не даёт:** ускорения сборки — крейт по-прежнему один, инкрементальная правка фронта
  так и стоит ~25 с полного цикла `trunk`. Границу по-прежнему не проверяет компилятор.
- **Риск:** комбинаторика фич. На 4 срезах это 16 конфигураций, из которых собирают две.

### C. 3 → 8 крейтов: ядро отдельно, маркетплейсы отдельно  *(рекомендуется)*

Минимальный разрез, отвечающий ровно на поставленный вопрос:

```
core-contracts   core-backend   core-frontend    ← kernel + system + catalog + gl + platform
mp-contracts     mp-backend     mp-frontend      ← mp_core + wb + ozon + ym
                 app-backend    app-frontend     ← composition root: роутер, реестр вкладок, main
```

`bi` на этом шаге остаётся в core. `llm` остаётся в core **навсегда** — см. §8.

- **Цена:** этап 0 (инверсия девяти хабов) + перенос ~78 k строк бэкенда и ~63 k фронта +
  правка `architecture.toml` и трёх генераторов. Недели, не дни.
- **Даёт:** границу, которую **проверяет компилятор** (обратное ребро просто не
  собирается); сборку без маркетплейсов; ускорение инкрементальной сборки фронта —
  правка в листовом крейте перестаёт перекомпилировать 177 k строк.
  *Оценка ~25 с → ~10 с; проверяется `tools/measure_build.ps1`, а не на слово.*
- **Не даёт:** модульной схемы БД (§4.1) — это отдельная работа.

### D. Полная вертикальная нарезка по 10 срезам (~26 крейтов)

`kernel / system / catalog / gl / mp-core / mp-wb / mp-ozon / mp-ym / llm / bi / platform`,
каждый в трёх тирах.

- **Цена:** кратно C. 26 манифестов, 26 наборов правил в `architecture.toml`, цикл
  сборки и `Trunk.toml` под каждый продуктовый вариант.
- **Даёт:** максимум изоляции и параллельной компиляции; поставку «только WB».
- **Когда:** только когда появится второй заказчик с другим набором, и только дорастив C.
  Начинать с D — платить всю цену до того, как известно, какие блоки реально комбинируются.

## 6. Рекомендация

**Этап 0 — инверсия хабов. Делать в любом случае, отдельно от решения о крейтах.**
Девять перечислений из §3 превращаются в реестры (трейт + регистрация в composition
root). Это полезно само по себе: снимает 11 из 26 обратных рёбер, чинит нарушение
«ядро знает о прикладном», и после него варианты A, B, C стоят заметно дешевле.
Проверяемый признак готовности: обратных рёбер ядро→маркетплейсы остаётся ≤ 10, и все
они — в хендлерах внешнего API.

**Дальше — по тому, что нужно раньше.** Нужен ответ организации на этой неделе → A
(поверх этапа 0). Нужна поставка без маркетплейсов → B. Нужна граница, которую нельзя
нарушить случайно, и более дешёвая сборка → C.

Сам по себе разрез на крейты **не** является ответом на «экземпляры для разных
организаций»: экземпляры уже разделены — свой `config.toml`, своя БД, свои скоупы.
Крейты покупают четыре конкретные вещи: размер поставки, время сборки, проверяемую
компилятором границу и возможность не отдавать чужой код. Если ни одна из четырёх не
болит — вариант A закрывает вопрос дешевле.

## 7. Чего в этом документе нет

- Отдельного замера `llm`: он сделан и вынесен в §8 — с обратным выводом.
- Модульных миграций (§4.1) — по объёму это отдельный план.
- Лицензирования: если «не поставлять маркетплейсы» означает ещё и «не дать включить»,
  это третья ось поверх сборки и скоупов.

## 8. Поправка: `llm` — это ядро, а не срез

*Добавлено 2026-08-29 после замера. Отменяет строку «Разреза `llm`» в §7.*

Исходная таблица §1 разложила код по **именам каталогов**, и механизм чата попал в
один ряд с маркетплейсами: `a018_llm_chat` выглядит как `a012_wb_sales`. Замер
зависимостей показал обратное.

### Куда смотрит ядро

Девять файлов ядра ссылаются в `llm`, и ни один из них не хаб-перечисление:

| Файл ядра | Зачем ему llm |
|---|---|
| `knowledge/collector.rs`, `summary.rs`, `tool_map.rs`, `llm_view.rs` | инвентаризация знаний **и есть** обход корпуса и реестра инструментов |
| `quality/checks/kb_integrity.rs` | quality-проверка целостности базы знаний |
| `system/datasets/restore.rs` | после восстановления набора перечитывает корпус и навыки |
| `shared/data/data_profile.rs` | профиль таблиц строится по `metadata_registry` |
| `plugins/service.rs` | плагин сохраняется как артефакт a019 |
| `processes/actions/create_agent_task.rs` | Действие ставит поручение агенту (a042) |

Плюс `system/metrics/collector.rs` → `knowledge`. Это не перечисления прикладных
имён, которые инвертируются реестром, — это ядро, пользующееся своей же
подсистемой. Убери `llm` — перестанут собираться инвентаризация знаний, quality,
восстановление наборов, профиль таблиц и публикация плагинов.

Сравнение с маркетплейсами, где вопрос разделения стоит по-настоящему: там таких
рёбер после Этапа 0 остался **один** файл, и тот — механический раздел файла
дашбордов. Разница не в количестве, а в природе: маркетплейсное ребро всегда
оказывалось списком имён, llm-ребро — вызовом механизма.

### Что из этого следует

1. **`shared/llm` — часть ядра, и правило `core_does_not_know_marketplaces`
   распространяется на него так же, как на `system/` и `quality/`.** Waiver'ы для
   `skills.rs` и `tool_executor.rs` сняты, реестр инструментов срезов заведён
   (`shared/llm/tool_provider.rs` + `composition/llm_tools.rs`): срез объявляет
   свои инструменты провайдером, ядро чата их имён не знает.
2. **Вариант D («llm отдельным крейтом») из списка выбывает.** Отделять надо не
   llm от ядра, а прикладные инструменты от чата — что и сделано.
3. **`a017`–`a019`, `a031`, `a038`, `a039`, `a042` — платформенные объекты в
   доменной нумерации.** Это и есть смешение, и у него нашлась цена: см. ниже.

### Цена смешения — не только косметика

`shared/data_access/raw_query.rs` классифицирует таблицу для сырого SQL **по имени**:
`aNNN_*` и `pNNN_*` считаются аналитическими. Исключения перечислены руками —
`a001_connection_1c` (креды 1С) и `a017`/`a018`/`a019` (корпус чата). Платформенные
`a031`, `a038`, `a039`, `a042` в исключения не попали и проходили как бизнес-данные.

Для `a038_llm_connection` это означало доступ к `api_key` провайдеров LLM:
пофамильный запрет поля в `sql_guard` `SELECT *` не ловит (звёздочка не называет
полей), а запрет звёздочки заведён только для `a006_connection_mp`. Закрыто:
`a038` добавлена в `is_secret_table`, тест
`llm_connection_is_never_reachable_by_raw_sql` держит все три профиля.

`a031_kb_edit`, `a039_mail_message`, `a042_agent_task` кредов не несут и оставлены
как есть — но классификация по префиксу имени остаётся способом, которым это
повторится. Правильный ответ — объявленный признак вместо угадывания по имени
(`metadata.json` уже несёт `ai.tags` и `llm_visible`); отдельная работа.

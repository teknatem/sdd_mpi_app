## 1. Мониторинг выполнения QuickJS на сервере. Статистика и метрики

Сделать мониторинг выполнения QuickJS на сервере. Статистика и метрики.

**Комментарий.** Рантайм — `rquickjs` в `crates/backend/src/plugins/engine.rs`:
лимиты 5 с / 64 МБ / 1 МБ стека, отдельный `AsyncRuntime` на вызов. Журнал
`plugin_run` уже считает длительность, ошибки, таймауты и «здоровье» плагина,
но skill-скрипты (`skill_runtime::run_task`) ходят в тот же движок мимо этого
журнала. Не хватает среза по самому рантайму: сколько контекстов живы сейчас,
кто съел лимит памяти/времени, какая доля вызовов — плагины, какая — навыки.

## 2. Глобальный реестр QuickJS

Сделать глобальный реестр QuickJS.

**Комментарий.** Скрипты сейчас лежат в двух местах, которые друг о друге не

## 3. Data to LLM text: БД → база знаний

Развивать технологию Data to LLM text. База данных — первичный источник, база
знаний — получатель. Например список организаций: сам список имеет описание
метаданных (статья KB), каждая организация — описание ключевых характеристик;
данные преобразуются в статьи. На выходе LLM может получить информацию об
оргструктуре бизнеса.

**Комментарий.** Заготовка уже есть: `kb_generated` на старте и по
`POST /api/kb/generate` пишет карты в `generated/` (профиль таблиц, плагины,
навыки, quality-checks). Это карты «строка на объект», не статьи, и они
намеренно выведены из обычного поиска. Пример с организациями (`a002`) — следующий
слой той же идеи: курируемый срез сущности → статья списка (метаданные) + статья
на запись, чтобы агент видел живую оргструктуру, а не схему таблицы. Нужны
правила, какие поля становятся текстом, как статьи стареют вместе с БД и как
не утопить поиск машинными карточками справочника.

## 4. Дебаггер чата LLM

Дебаггер для чата LLM с метриками, таймингами и т.д. для детального разбора
результатов и потраченных ресурсов.

**Комментарий.** Сейчас видно осколки, не разбор. В сообщении — `tokens_used` и
`duration_ms`, в пилюлях — `{tool, ok, ms}`, полный вход/выход инструмента
лежит в `sys_tool_trace` и открывается сбоку. Качество ответа меряет судья
(`docs/llm-quality.md`), а не стоимость прогона. Нет одного экрана на диалог:
итерации, prompt/completion/cached, время по стадиям, размер контекста, цена.
Без него непонятно, куда ушли токены и почему ответ занял 40 секунд.

## 5. Параллельная нагрузка на чат LLM

Проверить, как механизм чата LLM рассчитан на параллельную нагрузку и какие
там ограничения.

**Комментарий.** `POST .../messages` сразу отвечает 202 и делает `tokio::spawn`
без семафора. Дедуп только по `request_id` внутри одного чата; `ACTIVE_JOBS` —
множество id, не лимит. Потолок на практике — SQLite плюс параллельные циклы
инструментов, а не HTTP. Имеет смысл прогнать два сценария (N чатов сразу и
пачка сообщений в одном) и зафиксировать: сколько job'ов в полёте, что будет
при упирании в БД, нужен ли лимит на пользователя и на процесс.

## 6. MCP для внешнего подключения Cursor и Claude Code

Доработка MCP для внешнего подключения Cursor и CC.

**Комментарий.** Понимание: у MPI уже есть внутренний набор LLM-инструментов
(`tool_executor` и соседние модули) и внешний HTTP API (`/api/ext/v1/*` для 1С/BI),
но Model Context Protocol в репозитории нет. Задача — сервер MCP на работающем
экземпляре MPI, чтобы Cursor и Claude Code подключались к живым данным/инструментам
приложения, а не только читали исходники. Неясно: «доработка» значит, что заготовка
уже есть вне этого репо, или это с нуля? Транспорт — stdio (локальный процесс) или
HTTP/SSE к удалённому серверу? Какие тулы отдаём наружу (чтение KB/схем/SQL vs
мутации)? Как авторизуемся?

## 7. Стандартизация кнопок и команд UI

Стандартизация кнопок/команд UI. Закрыть, Провести, fullscreen... Один вид,
одно размещение, одно поведение.

**Комментарий.** Понимание: повторяющиеся команды шапки страницы сейчас
копируются с каждого экрана (`page-action-button`, то «Провести», то «Post»,
то иконка+спиннер). Нужен каталог именованных команд: один внешний вид, одно
место в `page__header-right` (или фиксированный слот), одно поведение — закрыть
вкладку, провести документ, развернуть на весь экран. Style guide описывает
наборы `.button` / Thaw, но не команды. Неясно: это компонент-реестр команд или
сначала письменный стандарт + проход по страницам? Fullscreen — вкладка, страница
или iframe плагина? «Закрыть» — всегда закрытие вкладки?

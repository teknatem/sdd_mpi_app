## Зачем

Три факта, каждый из которых по отдельности выглядит мелочью, а вместе они означают, что
знаниями сейчас не управляют, а надеются на них.

1. **Считается не то.** `/api/kb/stats` меряет markdown-статьи — примерно пятую часть
   того, откуда чат берёт знание. Реестр сущностей, источники данных, план счетов,
   quality-проверки, плагины, Процессы, Действия, навыки и каталог инструментов не
   посчитаны нигде.
2. **Курируемых статей ноль.** Знание об организации — то, ради чего база и заводилась, —
   отсутствует, и ни одна существующая метрика этого не показывает.
3. **Цена не измерялась.** До 2026-08-24 в журнале вызовов была длительность (`ms`), то
   есть «сколько ждали», но не «сколько заплатили контекстом». Главный расходуемый ресурс
   чата тратился вслепую.

Цель работ — замкнуть контур, в котором каждое решение о структуре знаний проверяемо:

```
реестр поверхностей → что ЕСТЬ и что ДОСТИЖИМО
        ↓
трасса вызовов      → что реально ДОСТАВЛЕНО и ПРОЦИТИРОВАНО
        ↓
Studio              → разрыв между этими числами, динамика за месяцы
        ↓
политика PD и корпуса → правка
        ↓
следующий снимок    → подтвердил эффект или нет
```

Без второго звена третье показывает объём вместо пользы, а четвёртое принимается на ощупь.

## Разделение: оперативно в MPI, стратегически в Studio

Граница проходит **по ритму и читателю**, а не по данным.

| | MPI (постоянно) | Studio (раз в недели) |
|---|---|---|
| Вопрос | что сломано сейчас | правильно ли устроен корпус |
| Форма | нарушитель поимённо, метрика с порогом | распределения, разрывы, тренд |
| Пример | статья без `summary`, битая ссылка, фантомное имя инструмента в навыке | доля `unreachable`, бюджет токенов по корпусам, `application` против `instance` |
| Читатель | тот, кто чинит сегодня | тот, кто решает, как устроить знания |

**Почему Studio не может собирать инвентарь сам.** Он статический анализатор
репозитория. База знаний лежит **вне репозитория**, плагины и Процессы — строками в БД,
ось достижимости (`skill_policy → tool_universe`) и группа «Ценность»
(`sys_kb_article_metrics`) существуют только в рантайме. Из 17 строк реестра §2 ему
доступны `code_embedded`, `code_registry` и, при удачном пути, `file_curated`. Инвентарь,
собранный из них, будет **молча неполным** — и политика построится на данных, где
отсутствует ровно то, ради чего база заводилась.

**Отсюда роль Studio:** он не считает, он показывает и сравнивает. Считает приложение.

**Чего в этом плане нет намеренно.** Наполнение курируемого корпуса. Любой шаг ниже
покажет ноль статей в первый же прогон, и на этом работа инструмента закончится: «кто и
по какому поводу пишет статьи» — это политика, инструментом она не заменяется.

## Что уже стоит (2026-08-24)

### Ш0. Цена вызова в токенах

- Миграция `0224_tool_trace_tokens.sql`: колонка `tokens` в `sys_tool_trace` плюс
  частичный индекс по ней.
- Считается по строке результата, **уходящей в модель** (`ChatMessage::tool_result`), а
  не по `output_json`: последний — отобранный whitelist'ом снимок для UI, он заметно
  короче доставленного, и мерить по нему значило бы занижать бюджет.
- Оценщик — `estimate_tokens` (`shared/llm/knowledge_base.rs`), тот же, что даёт
  `token_cost` статьям. Второй оценщик дал бы два несравнимых бюджета.
- Токены попали и в минимум для пилюль (`tool_trace_json`): цена шага должна быть видна,
  не открывая ящик. Гарды пишут 0 — они в модель ничего не шлют.

**Что это уже даёт:** самый дорогой инструмент виден по одному `SELECT`.
**Чего ещё не даёт:** привязки к единице знания — она в Ш2.

### Ш3. Разделы статьи — четвёртый уровень progressive disclosure

Три уровня PD в системе уже были: каталог инструментов (`CORE_TOOLS` + `use_skill`),
корпус (`generated` вне выдачи по умолчанию), документ (`summary` + `token_cost` в
поиске). Ниже документа уровня не было: `get_knowledge` отдавал `content` целиком.

- `knowledge_base::outline / section_text / intro_text` — разбор заголовков вне блоков
  кода. Делим по `##`; если их нет, а `#` больше одного (карты `generated`) — по
  `#`. Заголовки глубже уровня деления остаются **внутри** раздела: дробление до `####`
  дало бы огрызки вместо связных кусков.
- Разделы **не хранятся** в `KnowledgeDoc`: разбор стоит один проход и делается только
  при чтении конкретной статьи.
- `get_knowledge` получил три режима: `full` (как раньше), `outline` (крупная статья
  отвечает оглавлением и вводкой) и `section` (тело одного раздела). Порог —
  `SECTIONED_READ_TOKENS = 2000`, откалиброван по корпусу: средняя цена статьи `app` —
  1 316 токенов при максимуме 4 483.
- В выдаче поиска у таких статей стоит `sectioned: true` — модель узнаёт о режиме без
  лишнего вызова.

Два решения, которые стоит помнить:

- **Чтение оглавления не засчитывается как `read_hit`.** Иначе `read_hits` перестанет
  отличать «модель заплатила за текст» от «увидела оглавление», а на этой разнице стоит
  вся метрика полезности статьи.
- **`token_cost_last` остаётся ценой статьи целиком**, даже когда прочитан один раздел:
  это свойство статьи, а не цена вызова. Фактически доставленное меряет `sys_tool_trace.tokens`.

## Ш1. Модуль счёта — `system/knowledge/`

**Суть.** Один Rust-модуль поверх реестра поверхностей (§2 норматива), становящийся
единственным источником для четырёх потребителей: метрик, `/api/kb/stats`, страницы
«База знаний» и инструмента чата.

**Почему не в `shared/llm/`:** поверхности шире чата — Действия, разделы UI и план счетов
достижимы и через внешний API.

Состав:

- Перечислители по одному на строку реестра §2 (`EMBEDDED_LLM_DOCS`, `skills::snapshot()`,
  `quality::registry::snapshot()`, `plugins::repository::list_all`, `ALL_ENTITIES`,
  `SCOPE_CATALOG`, `processes::actions::list()`, `data_access::list_sources`, …).
- Семь осей на каждую единицу: происхождение, форма, кто правит, достижимость, жизненный
  цикл, область, канал раскрытия — плюс `code_role`.
- Токены — только через `estimate_tokens`.
- Таблица снимков `sys_knowledge_snapshot`, пишется при старте по образцу
  `sys_metric_snapshot`. **История живёт в приложении, а не в Studio:** иначе на новой
  машине Studio история исчезает, а у снимков появляется второй владелец.

**Приёмка:**

- числа сходятся с «Опорными цифрами» норматива (0 / 48 / 7 / 86 / 20 / 6 / 62 / 67 / 3+8 / 5);
- `/api/kb/stats` больше ничего не считает сам — он вид на модуль;
- инструмент чата отдаёт **агрегаты** по умолчанию и детали по явному запросу
  (`ARCHITECTURE.md` на 18 500 токенов — урок о том, чем кончается «отдать всё»).

**Ловушка:** не агрегировать сверх осей. Снимок повторяет реестр построчно; сводки
считает потребитель. Иначе через полгода в приложении появится вторая, своя аналитика
знаний.

## Ш2. Атрибуция вызовов по реестру

**Вопрос, на который отвечает шаг:** какие единицы знания получены на каком шаге диалога
и по какой цене.

**Механизм уже есть — его надо повторить, а не изобрести.** В `service.rs` инструмент
возвращает служебные поля `_activate_skill` / `_skill_access_level`, а слой трассы
собирает из них `SkillTraceEntry`. Тем же способом:

```
_units: [{ surface: "kb_app", unit_id: "projection-p916", tokens: 4483, mode: "read" }]
```

→ таблица `sys_tool_trace_unit(trace_id, chat_id, message_id, iteration, surface, unit_id,
tokens, mode)`, где `mode` = `search_hit` | `read` | `cited`.

Порядок:

1. `search_knowledge`, `get_knowledge` (с учётом режима: `outline` — не `read`),
   `use_skill` — это покрывает всё хранимое семейство.
2. Вычисляемые поверхности — синтетический `unit_id` (`entity:a015`, `source:dv001`) и
   токены по факту ответа.

**Ретро-парсинг `output_json` — разовая операция по накопленному журналу, не механизм.**
Как постоянное решение он ломается молча при первом изменении формата выхода инструмента.

**Объём.** Один поиск с 10 попаданиями — 10 строк. Нужна политика удержания сразу, иначе
таблица станет крупнейшей в базе; привязка к удалению чата — минимум.

**Приёмка:** по любому чату строится тройка «доступно → доставлено → процитировано», и
разрыв между вторым и третьим виден по конкретным статьям.

## Ш3′. Петля оптимизации PD (следует из Ш1 и Ш2)

| Сигнал | Откуда | Решение |
|---|---|---|
| Доставлено много токенов, цитирований нет | Ш2 + `cited_hits` | секционировать или сокращать |
| Находится поиском, но не читается | `search_hits` без `read_hits` | плохой `summary` — правится аннотация, не текст |
| Не тронута ни разу | `sys_kb_article_metrics` | вывести из выдачи через `status`, не удалять |
| Документ сверх порога токенов | Ш1 | очередь на секционирование |
| Поверхность без инструмента | Ш1, `unreachable` | завести инструмент либо решить «не раскрываем» |

**Пятый уровень PD** — вычисляемые поверхности: у них PD нет вовсе, инструмент отдаёт
что отдаёт. Нужен уровень «оглавление»: список сущностей → схема одной.

**Порог `SECTIONED_READ_TOKENS` пересматривается по данным Ш2, а не по ощущению.**
Сейчас 2 000 — калибровка по размеру корпуса, а не по наблюдению за чтением.

## Ш4. quality-check `kb_integrity`

Инварианты §7 норматива ложатся на модель quality-проверок (популяция / нарушения /
доля) один в один, а `quality/history.rs` и страница `quality_check_details_<id>` дают
то, чего метрика не даёт никогда: **нарушителя поимённо**. Число `dangling_links = 7` не
чинится; список из семи статей чинится.

Первая очередь: `summary` есть, тело не короче `MIN_BODY_CHARS`, `dangling_links`,
`unknown_anchors`, `unknown_tags`.

**Главное, что это закрывает:** сейчас три инварианта проверяются **только на запись**
через `kb_tools` и на статьи, попавшие в базу иначе (правкой в Obsidian, генератором), не
распространяются. Проверка применит их ко всему корпусу постфактум.

Исполнитель — `RustCheck` (нужен доступ к реестрам), не JS.

## Ш5. Эндпоинт и контракт со Studio

**Маршрут:** `/api/system/knowledge/inventory`, admin-only, JWT.

**Почему не `/api/ext/v1/*`:** там один общий ключ и анонимный потребитель, есть
контракт-тест на совпадение путей с `openapi.json`, и главное — внешний API описывает
*данные для клиента*, а инвентарь знаний это интроспекция устройства системы.

Отдаёт последний снимок и серию. Обязателен `schema_version`; потребитель, увидев
незнакомую версию, обязан сказать вслух, а не пропустить молча (правило стыка №2 канона —
тихий пропуск неотличим от «анализ не запускали»).

**Запись в `CONTRACTS.md`** как стык №4: направление приложение → Studio, носитель —
HTTP-ответ, владелец формата — приложение, недоступность экземпляра — не ошибка Studio.

**Побочный эффект, который надо назвать вслух:** у Studio появляется **профиль
подключения** (URL + токен) — тот же паттерн, что у Desktop. До сих пор он работал только
с файлами в каталоге; это расширение его природы, а не деталь конфигурации.

Не забыть: `ROUTE_REGISTRY` и `cargo test -p backend router_builds`.

## Ш6. Вьюер в Studio

Показывает: распределения по семи осям, разрыв «есть / достижимо / прочитано», бюджет
токенов по корпусам, сравнение снимков за месяцы.

Не показывает: списки нарушителей — это оперативная работа, её место в MPI (Ш4).

**Снимок обязан быть самодостаточным.** Studio не дочитывает ничего. Понадобилось поле
для картинки — оно едет в снимке. Иначе стык расползётся с одного ответа до «Studio знает
про приложение».

**Кросс-проектность — задел, а не выгода.** Манифест сегодня только у `sdd_mpi_app`,
сравнивать не с чем; строить вьюер под «много приложений» сейчас не надо.

## Ш7. Метрики `knowledge.*` (после стабилизации чисел)

Группа в `system/metrics/catalog.rs` рядом с `quality.*` и `docs.*`: 8–12 агрегатов, у
каждого направление и пороги.

**Гейтить храповиком можно только `application`-метрики.** `check_health.ps1` сравнивает
`codebase_metrics.json` — то есть статику, зависящую от кода: `phantom_tools`,
`unreachable_surfaces`, токены встроенного корпуса `app`. Экземплярные величины (число
`business`-статей, свежесть, ценность) в этот файл класть **нельзя**: коммит начнёт
блокироваться состоянием чужой БД. Ось «область применимости» из норматива — это и есть
граница между «гейтится» и «только наблюдается».

Ставить пороги раньше, чем числа перестанут ездить, — значит переставлять их каждую неделю.

## Решения по дороге и открытые вопросы

**Решено:**

- История снимков — в приложении (Ш1), Studio без состояния.
- Дверь наружу — внутренний admin-маршрут, не внешний API (Ш5).
- Оглавление статьи не считается чтением (Ш3).
- `token_cost_last` — цена статьи, не цена вызова; доставленное меряет трасса (Ш0).

**Открыто:**

- Удержание `sys_tool_trace_unit` — сколько хранить и по какому событию чистить.
- Порог `SECTIONED_READ_TOKENS` — пересмотреть по данным Ш2.
- **Контекстный режим** (§8 норматива, «что было доступно → что прочитал → чего не
  хватило») отложен решением 2026-08-23. После Ш2 он становится дешёвым: данные для него
  уже будут лежать.

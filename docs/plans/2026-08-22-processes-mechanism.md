## Зачем

Приложение умеет наблюдать (импорт → проведение в ГК → проекции → BI → AI-анализ), но
понятия процесса в нём не было. Исполнение размазано по пяти механизмам, которые ничего
не знают друг о друге: регламентные задания (30 шт., планировщик выключен), сессии
импортов `u5XX`, поручения агентам `a042`, quality-проверки и инструменты LLM-чата
(`shared/llm/*_tools.rs`, около 55 имён).

Не хватает им **не** долговечности как таковой. `a042` как раз живёт дольше запуска: там
статусы с легальными переходами, `attempts`/`next_attempt_at`, аренда `claim_session_id`
и условные `UPDATE` (`try_claim`, `release_stale`, `fail_exhausted`), а воркер `task029`
поднимает поручение после перезапуска сервера. Нет ни у кого другого: **графа с
курсором** («после какого исхода куда идём») и **ожидания по доменному событию**. Строим
именно это, а долговечность берём готовой конструкцией из `a042`, а не изобретаем
заново — см. Б5.

Пятый из этого списка — инструменты — не сосед, а вторая половина того же: библиотека
вызываемых операций. Она сливается с Действиями в один реестр, см. следующий раздел.

Цель работы — довести механизм до **одного настоящего процесса компании**: закрытия дня
WB. Внешних эффектов (маркетплейсы, 1С), рабочих мест по ролям, слоя планирования здесь
нет намеренно.

## Как связаны Процесс, Этап и Действие

Проще всего объяснить через то, что уже работает — quality-проверки на MJS: манифест плюс
модуль `check.mjs`, исполняемый в QuickJS (`plugins/engine.rs`) с ограниченным `host`.

```js
// базовая поверхность host — только чтение:
host.db.query(sql, params)   // разрешено по capability "db:read:<table>"
host.log.info(...)
```

Механизм — три достройки поверх этой конструкции.

**Действие** — новая ветка `host.actions`, у которой есть побочный эффект. Rust-функция под
своей `capability` (`action:repost_documents`), с обязательным вторым режимом (сухой
прогон) и ключом идемпотентности. *Действие = что система вообще способна сделать.*

**Этап** (`st0001`) — тот же mjs-модуль, но возвращает **один из заранее объявленных
выходов** и вправе звать Действия:

```js
export async function run(input, host) {
  const rows = await host.db.query("SELECT … FROM a033_wb_day_close …", [input.date]);
  if (rows[0].diff === 0) return { outcome: "сходится" };
  await host.actions.createAgentTask({ … }, { key: input.date });
  return { outcome: "расхождение", data: { amount: rows[0].diff } };
}
```

**Процесс** (`pr0001`) — граф: «после какого выхода Этапа идём в какой Этап», плюс триггер
и версия. Единственная по-настоящему новая сущность: у проверок и заданий графа нет.

**Экземпляр процесса** — строка в БД, живущая днями: курсор по графу, попытки, чего ждём.
Прогоны заданий живут ровно один запуск; экземпляр переживает перезапуск сервера.
Ожидание человека — это **состояние экземпляра**, а не отдельная подсистема (ADR-0011
п.9, п.13): инбокс есть список экземпляров, ждущих человека.

### Пилот целиком

```

                          │  триггер
   ┌──────────────────────▼───────────────────────── pr0001 «Закрытие дня WB» ──┐
```

> Имена и ключи здесь — **как в коде** (`backend/src/processes/pilot/`). Ключ
> корреляции — `connection_id` + `business_date`: так называются вход
> `rebuild_day_close` и колонки a033, и разойтись эти имена не должны.

Эффекты пилота **только внутренние**. Это выбор полигона: механизм проверяется на
настоящей работе без риска для денег.

## Один реестр методов: два флага, две оболочки

В первой редакции плана этого раздела не было вовсе, во второй он описывал инструменты
LLM-чата (`crates/backend/src/shared/llm/`) как соседний механизм, с которым надо
уживаться. Обе редакции неверны: у метода нет свойства «для кого он». Действия и
инструменты — одна библиотека вызываемых операций, у которой сегодня две несогласованные
половины. Реестр должен остаться один.

**Запись реестра** — имя, схема входа, право (`capability`), два описания (промпт для
модели и карточка для человека — тексты разные, поля разные) и два флага:

- **`effect`** — операция меняет мир. Тогда обязательны `plan()` (сухой прогон), ключ
  идемпотентности и запись в `sys_effect_log`. Где эффекта нет, журналировать нечего.
- **`needs_chat`** — операция работает над самим диалогом: `list_my_agent_tasks`,
  `get_chat_digest`, `read_chat_file`, `list_chats_for_review`. Вне диалога её нечем
  позвать — `chat_id` неоткуда взять. Список маленький и закрытый; всё остальное, включая
  чтение домена, доступно обоим вызывающим.

Оба флага выводятся **из самой операции**, а не из того, кто зовёт. Это и есть причина,
по которой механизм один, а не два.

**Оболочки тонкие, их две:**

| | Чат (`execute_tool_call`) | Этап (`host.*`) |
|---|---|---|
| Контекст | чат, агент, пользователь | экземпляр, Этап, режим |
| Вид ошибки | `{ok:false, error}` — модель читает и исправляется | исключение mjs; упавшее Действие → временный сбой |
| Ключ идемпотентности | чат + номер хода | экземпляр + Этап + визит |
| Право | матрица специализации | манифест Этапа |
| Защита от петли | `tool_guards` | лимит времени прогона |

Ключ в чате обязан включать **номер хода**: «сделай ещё раз» — законная просьба человека,
а повтор внутри одного хода — это ретрай модели, и он должен схлопываться.

Отсюда же: `host.actions` перестаёт быть отдельной «веткой эффектов» — это просто записи
реестра с `effect: true`, отобранные по манифесту Этапа. Читающие записи подключаются тем
же `HostExtensions`, и движок по-прежнему не знает, что такое Действие.

### Порядок работ

Переписывать полсотни инструментов разом не нужно и не будем: реестр эффектных операций
уже есть — это `processes::actions`.

1. **Сделано 2026-08-23 ✅:** `run_quality_check` и `create_agent_task` в чате делегируют в
   `actions::run` с `actor: User`. Двойной контракт исчезает, обе операции получают
   журнал. Попутно расширить результат `run_quality_check`: Действие отдаёт только
   `population_total`/`violations_total`, а инструменту нужен полный `details`.
2. **По мере касания:** `send_email`, `execute_funnel_repair`, `quality_check_upsert`,
   `plugin_upsert`, `ticket_create` переезжают в реестр. Каждый переезд снимает
   собственную самодельную защиту — `payload_hash`, проверку «превью показали в прошлом
   ходе», ручные лимиты — и заменяет её общей.
3. **Правило для нового:** операция с эффектом заводится в реестре, а не в `*_tools.rs`;
   инструмент над ней — адаптер. Второй реализации бизнес-логики не заводим никогда:
   и оболочка чата, и оболочка Этапа зовут один сервис домена.
4. **Инвариант живёт в сервисе, а не в вызывающем.** Общий потолок очереди поручений
   (`MAX_GLOBAL_BACKLOG`) переезжает из `agent_task_tools.rs` в `a042::service::enqueue`:
   это свойство очереди. Потолок на чат (`MAX_OUTSTANDING_PER_CHAT`) остаётся в оболочке
   чата — он про заказчика, а у Этапа заказчика нет.
5. **Сделано 2026-08-23 ✅. Имена полей одной операции совпадают в обеих оболочках.** У `create_agent_task`
   сейчас `context` (чат) и `payload` (Действие); канон — имя поля агрегата (`payload`),
   выравниваем при следующей правке инструмента, отдельного захода ради этого не делаем.

### Проверка реализации 2026-08-23

Сверка кода с этим разделом на простейшей операции, живущей в обеих оболочках —
`run_quality_check`. Что показала сверка и что из этого закрыто.

**Концепция держалась снизу и в mjs, но не в середине.** Второй реализации бизнес-логики
не было нигде: `quality::run_check_with_input`, `a042::service::enqueue`,
`shared/data_access/*` звались обеими сторонами. Един и mjs-рантайм — `plugins::engine`
обслуживает все четыре хоста (плагины, quality-проверки, задачи навыков, Этапы).
Не существовало **слоя оболочки как кода**: каждый вызывающий писал свою руками, и они
разошлись — у одной и той же операции в чате не было ни проверки входа по схеме, ни ключа
идемпотентности, ни строки в журнале.

Закрыто:

- **Пункт 1 «Порядка работ» ✅.** `run_quality_check` и `create_agent_task` в чате —
  адаптеры над `actions::run`. Оболочка чата вынесена в `shared/llm/chat_effects.rs`
  (`ChatEffect`): собирает актора, ключ `chat:<id>@<ход>:<действие>:<суффикс>` и приводит
  исход к `{ok, effect_id, replayed, …}`. Номер хода в ключе — прямой аналог номера захода
  у Этапа. Результат `run_quality_check` расширен до полного `details`.
- **Провенанс едет актором, а не входом.** `ActionActor::User` несёт диалог, агента и
  место в цепочке делегирования — ровно так же, как `Process` несёт экземпляр и Этап.
  Схема входа Действия осталась одной на обе оболочки: полей «для чата» у
  `create_agent_task` не появилось.
- **Пункт 4 ✅** (был сделан раньше), **пункт 5 ✅**: инструмент чата принимает и `payload`,
  и исторический `context`, вниз отдаёт канонический `payload`.
- **Обход права на Действие (баг).** `__hostActionCall` брал имя из JS и передавал в
  обработчик без сверки с выданным списком: Этап мог позвать любое Действие каталога мимо
  сахара `host.actions`. Инвариант «метода просто не существует» держал только сахар.
  Теперь имя сверяется на вызове (`engine.rs`), тесты — `ungranted_action_is_rejected_*`.
- **`get_project_metrics` не маршрутизировался (баг).** Объявлен, реализован, первый в
  навыке `app-health-review`, но ветвь диспетчера была захардкоженным `matches!` на четыре
  имени. Модель получала «Unknown tool». Заведена `ADMIN_TOOL_NAMES`.
- **Диспетчер.** Лестница из пятнадцати `if` с копипастой конверта `_tool`/`_ok` заменена
  таблицей `ROUTING_TABLE` + `route_of` + `finish`; тринадцать позиционных аргументов —
  типом `ToolContext`. Порядок ветвей перестал быть носителем смысла: три теста требуют,
  чтобы каждый объявленный инструмент имел маршрут, каждый маршрут — инструмент, а наборы
  не пересекались. Прежний комментарий «KB должен идти до kb_admin» больше не нужен.
  `tool_universe()` и `tools_catalog()` сведены к одному перечню `tool_bundles()`.

Открыто (каждое — отдельный заход):

- **Валидация аргументов инструмента по объявленной схеме.** `ToolDefinition.parameters` —
  JSON Schema, которая уходит модели и никогда не применяется к тому, что модель вернула.
  Часть инструментов спасается типизированным `parse_args::<T>`, часть читает
  `args.get(...)` с `unwrap_or_default()`. Одна точка в `execute_tool_call` и `jsonschema`
  (уже в зависимостях) это закрывают, но нужен прогон по всем ~88 схемам: неточная схема
  при строгой валидации сломает работающий вызов. Две операции, переехавшие в реестр, эту
  проверку уже получили — от `actions::run`.
- **Две модели прав на один SQL-путь.** Ядро одно (`sql_guard` + `row_json`), гейта два:
  `SqlAccessProfile` (три профиля, выведенные из `AgentType`, правила по префиксам таблиц
  захардкожены) у чата и `PluginCapability::DbRead(scope)` из манифеста у mjs. Вывод
  ADR-0010 обещает «единая capability-модель для обоих SQL-путей» — код обещание не
  выполняет. Сюда же разная строгость манифеста: quality-проверка обязана перечислить
  точные таблицы, Этапу разрешён `db:read:*`.
- **Курируемые источники для Этапа** — раздел «Чтение данных Этапом» выше. Упирается в
  зафиксированный там же вопрос про пересчёт `dvXX` мимо кэша.
- **Флаги `effect` / `needs_chat` как свойство записи.** Пока `effect` со стороны чата
  приближен двумя захардкоженными списками имён в `skill_policy.rs` (четыре имени на
  двоих), хотя мутируют мир также `send_email`, `ticket_create`, `quality_check_upsert`,
  `write_kb_document`, `create_drilldown_report`. Выводится это из пункта 2 «Порядка
  работ»: флаг появляется у записи тогда, когда операции переезжают в реестр.

### Чтение данных Этапом

Сегодня Этап читает **только** сырым SQL — `host.db.query`. Гард настоящий: запрос
разбирается, таблицы сверяются с `db:read:<таблица|тег>`, строки ограничены лимитом. Но
по ADR-0010 сырой SQL — укреплённый escape-hatch, а не основной путь: чат давно ходит
через курируемые метрики, а Этап пишет SQL руками. Это регресс у младшего, а не разница
механизмов.

**Решено:** Этапу даётся **несколько способов извлечения данных — с кэшем и без, — и
выбирает между ними код самого Этапа.** Выбор зависит от контекста вызова, а не от вида
операции, поэтому решать его должен тот, кто знает контекст. Это тот же принцип, что в
ADR-0010: роль источника выбирают осознанно.

- **Курируемая метрика (`dvXX`)** — когда нужен уже определённый кем-то показатель и
  допустима кэшированная величина: обзор, сводка, порог «по последним данным».
- **Безопасная схема (`dsXX`) или прямой запрос** — когда решение принимается по свежему
  состоянию: сверка, ответ на «сходится ли», всё, за чем сразу идёт эффект.
- **Сырой SQL** — остаётся как есть, для разового.

Что проверить до того, как выдавать Этапу `dvXX`: можно ли потребовать пересчёт мимо
кэша. Человек в чате заметит, что число вчерашнее, и переспросит; Процесс не переспросит
и проведёт эффект. Если пересчёта по требованию нет — Этапам достаются только
некэшированные пути, а `dvXX` остаётся справочным.

Четыре Действия, все внутренние, все поверх готовых сервисов: `rebuild_day_close` (a033),
`repost_documents` (u508), `run_quality_check` (quality), `create_agent_task` (a042).

Устройство, которое важно не потерять:

- Запись в журнал делается **до** исполнения. Иначе падение между эффектом и записью
  делает эффект невидимым, а повтор — вторым.
- Идемпотентность держит **уникальный частичный индекс БД** (`WHERE mode = 'execute'`), а
  не проверка в коде: два воркера обязаны разойтись на уровне базы. Планы сухого прогона
  ключ не занимают — иначе просмотр плана закрыл бы дорогу настоящему исполнению.
- Незавершённая запись (`in_progress`) после падения — **не повод повторить**, а повод для
  разбора: что произошло с миром, неизвестно (ADR-0011 п.10).
- `action:*` намеренно не разбирается в право: чтение обратимо, проведение документа — нет,
  поэтому эффекты выдаются поимённо.

| Статическая проверка | `backend/src/processes/stages/validate.rs` |
| Шов в рантайме | `backend/src/plugins/engine.rs` — `HostExtensions` |

Устройство:

- **Ветка `host.actions` инжектируется, а не зашита в движок.** Движок получил
  `HostExtensions { actions: Option<(Vec<HostActionEntry>, HostActionHandler)> }` и не знает,
  что такое Действие. Плагины и навыки идут прежним путём и ветки эффектов не видят вообще:
  право не отбирается проверкой, его просто не выдают.
- **Права и режим захвачены замыканием на стороне Rust**, а не прочитаны из глобала JS.
  У соседнего `__hostCapabilitiesJson` эта слабость есть — скрипт может присвоить себе
  другой глобал; для эффектов её повторять нельзя. Поэтому сухой прогон Этапа не может
  исполнить настоящий эффект, что бы ни написал автор mjs.
- **Ключ идемпотентности выводится из контекста прогона**:
  `{экземпляр|manual}:{этап}:{действие}:{options.key|порядковый}`. Повтор Этапа после
  падения воркера не делает эффект вторым; смысловой `options.key` переживает и
  перестановку вызовов внутри Этапа.
- **Три класса исхода разделены механически** (`StageVerdict`): упавшее Действие
  отмечается флагом на стороне Rust, поэтому временный сбой отличается от дефекта Этапа не
  разбором текста исключения, а фактом. Выход, не объявленный в манифесте, — дефект: автор
  не может объявить `error` и увести дефект в штатную ветку.
- Лимит времени прогона Этапа — 300 с (у плагинов 5 с, у проверок 30 с): Этап ждёт
  Действий, а перепроведение идёт минутами.

### Открытые места Б2 (найдены на второй сверке 2026-08-22) — закрыты в Б5

> **Все три закрыты**, см. раздел Б5. Формулировки ниже оставлены как есть: они объясняют,
> почему решения в Б5 именно такие, и стоят дороже, чем отметка «сделано».

1. **Ключ идемпотентности не переживает цикл в графе.** Ключ —
   `{экземпляр|manual}:{этап}:{действие}:{options.key|порядковый}`. В пилоте есть цикл
   st0004 → st0001: на втором заходе ключ тот же, вызов вернётся `replayed`, и
   `rebuild_day_close` **ничего не пересчитает** — ровно то, ради чего в цикл и
   возвращались. Смысловой `options.key` (например, дата) не спасает: он тоже не
   меняется. Нужен номер визита из состояния экземпляра — четвёртой частью ключа. Пока
   экземпляров нет, дефект не проявляется: ручные прогоны единичны.
2. **`in_progress` = карантин конфликтует с гонкой двух воркеров.** Проигравший гонку на
   уникальном индексе получает ошибку вставки → временный сбой → повтор → видит
   `in_progress` → «требуется разбор». Карантин из-за штатной конкуренции, а не из-за
   падения. Разводится тем же, чем в `a042`: эксклюзивной арендой экземпляра
   (`claim_session_id` + `release_stale`) — тогда `in_progress` действительно означает
   «кто-то умер», а не «кто-то работает прямо сейчас». Плюс `in_progress` нечем
   протухнуть и негде разобрать: `effect_log::list_recent` есть, экрана нет (Б6).
3. **Таймаут Этапа классифицируется как дефект, хотя обычно это временный сбой.**
   Прерывание QuickJS срабатывает между операциями байткода: пока скрипт ждёт Действие,
   движок не исполняется, поэтому лимит в 300 с длинный репост **не режет** — тот доходит
   до конца, а прерывание случается на возврате. `action_failure` при этом пуст (Действие
   успешно), и Этап уезжает в карантин при уже состоявшемся эффекте. Лимит и ставился
   «потому что перепроведение идёт минутами», то есть это ожидаемый случай, а не
   экзотика. Отличить таймаут можно: `error.downcast_ref::<PluginError>()`, поле
   `stage == "timeout"`. Открытый вопрос — заводить ли четвёртый класс исхода или
   отображать таймаут в `TemporaryFailure`; решает Б5, потому что решает это тот, кто
   считает попытки.

### Б3 — хранение и версии определений ✅

| Что | Где |
|---|---|
| Граф Процесса, ожидание, критичность | `contracts/src/processes/process.rs` |
| Хранимая версия, diff, план активации | `contracts/src/processes/definition.rs` |
| Таблицы определений | `migrations/0220_process_definitions.sql` |
| Запросы | `backend/src/processes/repository.rs` |
| Статическая проверка графа | `backend/src/processes/graph.rs` |
| Жизненный цикл и гейт активации | `backend/src/processes/definitions.rs` |

Устройство, которое важно не потерять:

- **Версия — это строка, а не колонка.** Каждая публикация заводит `(code, version)`;
  опубликованное (`active`/`archived`) не редактируется и не удаляется вообще. Правило
  «версия не удаляется, пока на неё ссылаются» реализовано сильнее, чем сформулировано в
  ADR: ссылку проверять не нужно, потому что удаления опубликованного нет как операции.
  Удалять можно только черновик — на него сослаться ещё некому.
- **Черновик один на код и правится по месту** (частичный уникальный индекс). Иначе
  история версий заросла бы нажатиями «сохранить», и вопрос «что изменилось с прошлой
  публикации» пришлось бы решать глазами. Активная версия тоже одна на код, и это тоже
  индекс БД, а не порядок операций в коде.
- **Пины Этапов фиксируются в момент активации Процесса**, а не на старте экземпляра —
  уточнение к ADR-0011 п.7, записанное в самом ADR. Причина: Этапы лежат в глобальном
  каталоге и переиспользуются, поэтому публикация Этапа иначе меняла бы поведение чужих
  Процессов молча. Теперь она видна следующим планом активации — и именно это делает
  двухуровневый diff реализуемым: «Процесс не менялся» ничего не значит, если под ним
  поменялся Этап, и сравнивать есть с чем только потому, что прошлые пины записаны
  (`pins_json`).
- **Активация — гейт, а не кнопка.** `activate_process` считает тот же план, что показан
  человеку, и отказывает на тех же основаниях: просмотреть план и обойти его нельзя.
- **Критичность выведена из прав Этапов** (ADR-0011 п.4), порог — первый же эффект, а не
  необратимость: рассогласование остаётся видимым нарушением независимо от того,
  откатывается ли эффект. Парная quality-проверка обязана **существовать** в каталоге, а
  не быть упомянутой: ссылка на незаведённую проверку — это отсутствие видимости, поданное
  как её наличие.
- **Граф проверяется статически** (ADR-0011 п.11): выход, которого нет в манифесте Этапа;
  выход без ребра (терминал объявляется целью `done`, а не молчанием); недостижимый Этап;
  ожидание без дедлайна; непокрытое обязательное поле входа. Вход Этапа считается
  объединением ключа корреляции экземпляра и данных выхода предыдущего Этапа — это
  правило записано в `graph.rs` и его должен соблюдать воркер Б5.
- `stages::validate::digest()` подключён: отпечаток считается при сохранении и лежит в
  строке. Отпечаток Процесса — `graph::digest()`.

Чего в Б3 намеренно нет: API-роутов и экранов. Определения вне git, поэтому смотреть их
можно только в приложении — но экран версий и diff-а идёт вместе с остальными экранами
механизма в Б6, чтобы не заводить UI дважды.

### Б4 — доменные события ✅

| Что | Где |
|---|---|
| Каталог событий и ключ корреляции | `contracts/src/processes/event.rs` |
| Журнал фактов | `migrations/0221_sys_domain_event.sql`, `backend/src/processes/events.rs` |
| Проверка триггера по каталогу | `backend/src/processes/graph.rs` |

Пять событий, ровно как в плане: `import.day.completed`, `document.posted`,
`quality.violation.raised`, `human.action.done`, `process.instance.timeout`.

Устройство:

- **Ключ корреляции — свойство факта, а не подписки.** Состав ключа задан каталогом
  (`DomainEventKind::correlation_fields`), и поле `correlation` из триггера Процесса
  **убрано**: объявляй ключ подписчик, два Процесса разошлись бы в том, что считать «тем
  же самым днём». Имена полей взяты из домена, а не из плана: у `import.day.completed` это
  `connection_id` + `business_date` — ровно вход `rebuild_day_close`.
- **Ключ сводится к токену** `поле=значение;поле=значение` в порядке каталога. По
  равенству токенов ожидающий экземпляр находит своё событие, поэтому состав ключа
  проверяется на публикации **точно**: неполный ключ и лишнее поле одинаково означают, что
  токен не сойдётся, а потеря будет молчаливой.
- **Журнал только дописывается, доставки нет.** Строка не помечается прочитанной:
  читателей у факта может быть от нуля до всех ожидающих экземпляров. Позицию держит
  потребитель — курсор по `seq` (AUTOINCREMENT, а не время: время в SQLite не монотонно
  между процессами).
- **`human.action.done` держит ключ `request_key`** — токен экземпляра, попросившего
  человека. Событие общее для всех Процессов, а «про что оно» знает тот, кто просил.
- **Триггер и ожидание проверяются по каталогу**: событие не из каталога — дефект
  манифеста, а не повод завести событие строкой. Вход стартового Этапа проверяется на
  покрытие ключом корреляции этого события.
- **Заглушка `EventStore` удалена** вместе с полем `BaseAggregate.events` и парой методов
  `AggregateRoot` (45 файлов). Она ничего не делала с 2025 года, но занимала имя: двух
  разных «доменных событий» в кодовой базе быть не должно, и выбор был «занять или
  удалить».

**Производителей событий в коде пока нет, и это намеренно.** Точка публикации — часть
смысла факта: «день импортирован» это конец какого именно импорта, при каком составе
данных. Решать это без пилота значит угадывать, а ошибка здесь дороже отсутствия: лишний
факт запускает Процесс. Публикация расставляется в Б6 вместе с пилотом; `human.action.done`
публикует кнопка инбокса, `process.instance.timeout` — воркер Б5.

Решено на сверке: `create_agent_task` в пилоте — **fire-and-forget**. События «поручение
исполнено» в каталоге нет, и Процесс исхода поручения не ждёт. Понадобится ожидание —
добавим шестое событие, а не будем опрашивать `a042` из Этапа: опрос обходит границу
решения №5 (что является фактом, решает ядро).

### Б5 — воркер экземпляров ✅

| Что | Где |
|---|---|
| Состояние экземпляра | `contracts/src/processes/instance.rs`, `migrations/0222_sys_process_instance.sql` |
| Хранилище и переходы | `backend/src/processes/instances.rs` |
| Проход воркера | `backend/src/processes/worker.rs` |
| Запуск в рантайме | `backend/src/main.rs` (шаг после регистрации заданий) |

Один проход (`worker::tick`) делает четыре вещи: снимает брошенные аренды, разбирает
новые события (старт по триггеру и пробуждение ожидающих), исполняет очередной Этап у
готовых экземпляров, разбирает просроченные ожидания. `tick` вынесен отдельной публичной
функцией именно ради тестов: проверять решения воркера через таймер бессмысленно.

**Три открытых места Б2 закрыты — и это главный результат вехи:**

1. **Ключ идемпотентности переживает цикл.** В состоянии появился `visit` — номер захода;
   ключ стал `{экземпляр}:{этап}@{визит}:{действие}:{суффикс}`. Проверено тестом
   `a_second_visit_to_a_stage_is_not_a_replay`: граф с циклом, один и тот же смысловой
   `options.key` на обоих заходах, и в журнале эффектов две записи с разными ключами.
   Повтор **того же** захода после сбоя номер не меняет, поэтому защита от двойного
   эффекта осталась на месте.
2. **`in_progress` снова означает «кто-то умер».** Аренда (`claim_session_id` + условный
   `try_claim`) не даёт двум воркерам взять один экземпляр, поэтому незавершённая запись
   журнала больше не может быть следствием штатной конкуренции. Брошенную аренду снимает
   `release_stale` через 30 минут — с обязательным фильтром по `status = running`, иначе
   развёртка стоптала бы экземпляр, который только что дошёл до ожидания.
3. **Таймаут Этапа — временный сбой, а не дефект.** Отличается фактом, а не текстом:
   `PluginError::stage == "timeout"` (движок помечает так в `relabel_timeout`). Решение
   именно такое, потому что прерывание QuickJS срабатывает между операциями байткода:
   долгое Действие доходит до конца, а лимит бьёт уже на возврате — карантин при
   состоявшемся эффекте был бы худшим из исходов.

Остальное устройство:

- **Уникальный живой экземпляр на пару «Процесс + ключ корреляции»** — частичный
  уникальный индекс. Повторный факт про тот же день не заводит второй прогон; проигравший
  гонку читает конфликт как «уже идёт», а не как ошибку.
- **Маршрут после пробуждения не хранится в состоянии.** Экземпляр помнит курсор и
  последний выход, а куда по ним идти — читается из графа запиненной версии. Так остаётся
  один источник истины о маршруте, и он тот, на котором экземпляр стартовал.
- **Ожидание собирается из того, что экземпляр знает о себе**: ключ корреляции, свой токен
  (`request_key` — им адресуется просьба к человеку), свой идентификатор, данные выхода.
  Несобравшийся токен — дефект, и **он ловится статически**: `graph.rs` проверяет
  заполнимость ключа ожидания на активации, потому что узнать об этом через сутки на живом
  прогоне — значит потерять сутки.
- **Дедлайн публикуется фактом** `process.instance.timeout`, а не только пишется в строку:
  «истекло» — такое же событие домена, и его может ждать другой Процесс. Дальше экземпляр
  идёт по запасному ребру или остаётся человеку.
- **Ретраи**: 1 → 5 → 15 → 30 минут, потолок пять попыток, дальше карантин. Отдельного
  статуса «ждёт повтора» нет — есть `next_attempt_at`, как в `a042`.
- **Координатор ресурсов подключён по-настоящему**: у Действия появилось поле
  `write_tables` (`ActionInfo`), и Этап берёт объединение таблиц своих Действий перед
  прогоном. Конфликт с импортом в те же таблицы означает «сейчас нельзя», а не «сломалось»:
  экземпляр просто ждёт следующего прохода.
- **Воркер запущен в `main.rs` и не зависит от флага планировщика** (ADR-0011 п.12).
  `[scheduled_tasks].enabled = false` не тронут. Пока не активирован ни один Процесс,
  проход — четыре пустых запроса раз в 30 секунд.

Мелочь, о которую спотыкается всякий, кто будет писать здесь тесты: проход воркера
**глобален**, а тесты одного бинаря делят базу. Поэтому `processes_worker.rs` держит
собственный мьютекс и утверждает про состояние своего экземпляра, а не про счётчики
прохода — чужой проход двигал бы наш экземпляр между нашими же проверками.

### Б6 — пилот pr0001, инбокс и допуск ✅

| Что | Где |
|---|---|

| Действие «позвать человека» | `backend/src/processes/actions/request_human_action.rs` |
| Журнал шагов экземпляра | `migrations/0223_sys_process_step.sql`, `backend/src/processes/steps.rs` |

| HTTP-поверхность (admin-only) | `backend/src/api/handlers/processes.rs`, `api/routes.rs` |
| Страница «Процессы» | `frontend/src/processes/`, `static/pages/sys_processes.css` |
| Точка публикации факта | `u504 …/executor.rs` — `publish_completed_days` |

**Решение по st0003, которое ждали.** Взят первый вариант из двух: «день закрыт» =
снимок a033 существует, пересчитан и без блокирующих проблем. Состояние закрытия в
домене **не заводили** — домен не расширяется под механизм. Чтобы Этап при этом не
дублировал st0002, вопросы разведены: st0002 смотрит **результат** сверки (блокирующие
проблемы детекторов a033 и есть сверка дня), st0003 — **свежесть самого снимка**
(`last_recalculated_at`, `snapshot_hash`). Пересборка могла тихо не состояться, и тогда
«сходится» означало бы лишь то, что проблем не нашли во вчерашних данных.

Устройство остального:

- **Пилот засевается черновиками при старте** (`pilot::seed`) и **не активируется**:
  активация — решение человека с просмотром плана (ADR-0011 п.8). Посев не трогает то,
  что уже есть в базе: после первого запуска источник истины — БД, а файлы в репозитории
  остаются образцом. Граф пилота проходит тот же валидатор, что и чужие, — это покрыто
  тестом, потому что образец, не проходящий собственную проверку, хуже отсутствия
  образца.
- **`request_human_action` порождает `sys_ticket`**, а не четвёртую очередь к человеку —
  ровно как записано в этом плане. Ключ просьбы — **токен корреляции экземпляра**, а не
  его id: тем же ключом адресуется `human.action.done`, и на id «сделано» никогда не
  сошлось бы с ожиданием. Известное ограничение: автор тикета синтетический
  (`process`), а список тикетов фильтруется по автору — значит, такие тикеты видны
  администратору, а обычному пользователю просьба видна в инбоксе механизма.
- **Журнал шагов** (`sys_process_step`) — не дубль журнала эффектов: там изменения мира,
  здесь решения. Этап без эффектов не оставит в журнале эффектов ни строки, а его выход
  определил маршрут — без этого разбирать прогон нечем.
- **Парная проверка QC-010 «WB: незакрытые дни»** считает популяцией дни, по которым были
  продажи (закрывать нечего там, где ничего не продано), а нарушением — день без снимка,
  без пересчёта либо с блокирующими проблемами. Ровно то же определение закрытия, что у
  st0003: два определения одного факта разошлись бы через неделю.
- **Точка публикации `import.day.completed`** сужена тремя условиями: импорт закончился
  **чисто** (`Completed`, не `CompletedWithErrors`), в задании были **продажи**
  (`a012_wb_sales`), и **сегодняшний день не публикуется** — он ещё накапливается. Плюс
  потолок в 62 дня за один импорт, чтобы годовая перезаливка не превратилась в сотни
  экземпляров одним махом.
- **Страница «Процессы»** (admin-only, `sys_processes`) — три вкладки: экземпляры с
  инбоксом и разбором, определения с планом активации и сухим прогоном, журналы эффектов
  и событий. Кнопка «Сделано» не двигает экземпляр — она публикует факт, а двигает
  воркер; кнопка «Двинуть сейчас» рядом существует только чтобы человеку не ждать
  очередного прохода.
- **Потолок очереди поручений переехал в `a042::service::enqueue`.** Пока он жил в
  инструменте чата, поручения от Процесса обходили его молча. Потолок на один чат остался
  в оболочке чата: он про заказчика, а у Этапа заказчика нет. Обратная ссылка на
  экземпляр у поручений от Процесса едет в `payload_json` — подходящей колонки нет:
  `requested_by_*` это чат, агент и пользователь.
- **`ActionInfo` получил `write_tables`**, и воркер берёт под Этап объединение таблиц его
  Действий через общий `resource_coordinator`. Конфликт с импортом в те же таблицы
  означает «сейчас нельзя», а не «сломалось».

**Чего в Б6 намеренно нет:**

- **Теневого режима** (ADR-0011 п.8) — сухой прогон Этапа есть, прогона всего Процесса на
  реальных событиях без эффектов нет. Он имеет смысл, когда пилот уже отработал вживую;
  до того это конструкция без пользователя.
- **Редактора определений в UI.** Определения правятся через API; страница показывает и
  допускает, но не редактирует. Первые Этапы писал человек, следующие будет писать LLM
  через тот же API — редактор в браузере не на этом пути.
- **Активированного пилота.** Он засеян черновиками; включать — по явному решению, глядя
  на план активации.

### Отложено по существу

- **`post_document`** — обобщённого «провести» в коде нет: проведение живёт в `posting.rs`

### Правки соседнего кода

- `RepostExecutor::repost_aggregate_inline` — синхронный вход в u508. Существующий

- `llm/skills.rs` — задача навыка, просящая `action:<name>`, снова отвергается на

## Грабли этой работы

- **`backend.exe` блокирует `cargo test`.** `cargo test` пересобирает и бинарь; запущенный
  сервер держит файл, сборка падает на «Отказано в доступе». Сейчас сервер **остановлен и
  не поднят**; поднимать — `powershell -File tools/run_backend.ps1`.
- **Тесты одного бинаря делят базу и идут параллельно.** База своя на процесс
  (`backend-test-<pid>.db`, удаляется на старте), но внутри бинаря она общая. Мерить эффект
  глобальным счётчиком (`count_open()`) нельзя — проверка становится плавающей. Мерить надо
  адресно: журнал эффектов привязан к ключу идемпотентности, и раз каждый эффект проходит
  через него, отсутствие боевой записи по ключу и есть отсутствие эффекта.
- **`cargo fmt` трогает чужое.** В репозитории есть заранее неотформатированные файлы
  (`metadata_gen.rs` — их пишет `build.rs`, CI их фильтрует; плюс `a004_nomenclature`,
  `admin_tools`, `router`, `wildberries_api_client`). Форматировать точечно:
  `rustfmt --edition 2021 <свои файлы>`.
- **Heredoc через агентскую оболочку рвёт длинные файлы и схлопывает обратные слэши.**
  Крупные исходники писать инструментом записи файлов; в TOML помнить, что `\d` внутри
  basic string — недопустимый escape, нужен `\\d`.

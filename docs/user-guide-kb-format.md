# Пользовательская документация в базе знаний

Раздел `user-guide` базы знаний — источник, из которого AI-помощник берёт ответы на
вопросы «как этим пользоваться». Инструмент `find_page_help(page_key)` ищет статьи по
тегам, привязанным к странице приложения.

## Где лежит

Файлы `*.md` в каталоге знаний (`<[data].root>/knowledge` из `config.toml`, сейчас
`F:/data/sdd_mpi_app/knowledge/`) — **вне репозитория**, чтобы статьи можно было
править без пересборки. Каталог перечитывается по `POST /api/kb/reload` (кнопка
«Перечитать базу» в разделе «База знаний») и при старте бэкенда.

Существующие образцы: `ug-getting-started.md`, `ug-tickets.md`, `ug-sales-report.md`.

## Формат

```markdown
---
title: Отчёт по продажам
tags: [user-guide, page:p904_sales_data, p904_sales_data, продажи, отчёт]
related: [p904]
updated: 2026-08-02
---

# Отчёт по продажам

...текст статьи...
```

Обязательные теги:

| Тег | Зачем |
|---|---|
| `user-guide` | Помечает статью как пользовательскую (а не как справку по домену или для разработчика) |
| `page:<tab_key>` | Привязка к странице приложения. `tab_key` — ключ вкладки: `p904_sales_data`, `sys_tickets`, `d400_monthly_summary` |

Дальше — обычные тематические теги (`продажи`, `реклама`, `возвраты`): по ним статью
находит `search_knowledge`, когда пользователь спрашивает не про конкретный экран.

Для карточек объектов тег ставится на **базовый ключ списка**: `find_page_help` сам
отбрасывает суффикс `_details_<id>`, поэтому отдельная статья на каждый объект не нужна.

Имя файла = идентификатор статьи (`ug-sales-report.md` → `ug-sales-report`), его
возвращает `find_page_help` и по нему же читается полный текст через `get_knowledge(id)`.
Префикс `ug-` — соглашение, не требование движка.

## Как писать

Статью читает **LLM, а потом пересказывает пользователю** — поэтому:

- пишите про то, что видит пользователь (кнопки, фильтры, колонки), а не про таблицы
  и код;
- отдельным разделом — типовые «почему цифры не сходятся» и «что проверить сначала»:
  именно это чаще всего спрашивают;
- никаких обещаний по срокам и планам развития;
- ссылки на другие статьи — по их идентификатору: `[Обращения](ug-tickets)`.

## Что дальше

Каркас готов: теги, инструмент поиска и три статьи-образца. Наполнение остальных
разделов — отдельная задача; писать статьи может и LLM через `kb_admin_tools`
(`write_kb_document`), но проверять содержание должен человек, знающий предметную область.

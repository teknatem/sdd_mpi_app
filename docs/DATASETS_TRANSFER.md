# Наборы данных и перенос между экземплярами

Подсистема решает две сцепленные задачи: приводит файловые данные приложения к
одной предсказуемой раскладке и даёт перенести выбранные наборы с одного
экземпляра на другой (рабочий ↔ тестовый) через S3, с диагностикой источника и
предварительным сравнением.

UI: сайдбар → «Администрирование» → **«Наборы данных и перенос»** (admin-only,
scope `sys_datasets`).

---

## 1. Раскладка на диске

```
<data_root>/
  db/  knowledge/  skills/  chats/  golden_set/
  quality_checks/  attachments/  backups/  tmp/
```

Эти девять каталогов создаются при старте (`datasets::bootstrap::ensure_data_root`).

`db/` — место файла БД вместе с `-wal`/`-shm`; без явного `[database].path` база
живёт в `<data_root>/db/app.db`. Держать базу в самом корне данных не стоит: при
переносе каталога легко утащить трёхгигабайтный файл вместе с мелкими наборами,
а `-wal` отстать от своей базы.

**Основной режим — один путь в конфиге.** `[data].root` задаёт корень, всё
остальное выводится из него; индивидуальные пути в своих секциях — отклонение,
которое нужно осознанно выбрать. Путь каждого каталога резолвится в три уровня
(`shared/config.rs`, `resolve_dataset_dir` и `resolve_database_path`), в порядке
убывания приоритета:

| Приоритет | Условие | Результат | `PathOrigin` |
|---|---|---|---|
| 1 | В своей секции задан **абсолютный** путь (`[database].path`, `[llm].skills_path` и т.п.) | путь как есть | `LegacyOverride` («Индивидуальный путь») |
| 2 | Задан `[data].root` | `<root>/<имя>` | `DataRoot` |
| 3 | Иначе | относительно каталога бинарника | `ExeRelative` |

Первый уровень — для случаев, когда каталог обязан жить в другом месте (база на
отдельном диске, общая база знаний), и заодно сохраняет старые конфиги с
абсолютными путями рабочими байт-в-байт. Третий остался только как историческое
поведение: конфиг без `[data].root` и без `[database].path` старт отвергает.

`PathOrigin` показывается в UI отдельной колонкой, а каждое отклонение попадает
в аномалии (`path_override`, Info) — видно, какие каталоги «выбиваются» из общего
корня и не участвуют в переносе. Отклонения перечисляются и в стартовой
диагностике строками `!`.

### Конфиг

```toml
[data]     root  = "F:/data/sdd_mpi_app"   # единственный путь в основном режиме
[instance] id = "prod-01"  label = "Рабочий"  env = "production"   # production|staging|dev
[datasets] keep_per_instance = 10  max_bundle_mb = 256  attachments_enabled = false
```

`[data].root` обязан быть абсолютным (относительный «переезжал» бы вслед за
рабочим каталогом процесса) и обязателен, если не задан `[database].path`.
`[instance]` и `[datasets]` опциональны. Пустой `[instance].id` → имя машины; `label` → `id`.
**Hostname пишется в манифест всегда**, даже при явном `id`: два снапшота с
одинаковым `id`, но разными машинами — признак скопированного и не поправленного
`config.toml`, и UI об этом предупредит.

### Что изменилось в существующих данных

- **Вложения чатов.** Раньше `a018_llm_chat_attachment.filepath` хранил путь
  относительно рабочего каталога процесса (`uploads/chat_attachments/...`) —
  запуск бэкенда из другой директории «терял» вложения. Теперь в БД лежит ключ
  относительно корня вложений (`<chat_id>/<uuid>.<ext>`). Миграция
  `0210_attachment_filepath_relative.sql` переписывает старые строки (обе формы
  слешей), `attachment_abs_path` в `domain/a018_llm_chat/service.rs` понимает обе
  формы, а `datasets::bootstrap::migrate_legacy_attachments` при старте переносит
  сами файлы — но только если целевой путь стабилен (задан `[data].root` или
  абсолютный override). Иначе вложения переехали бы в каталог рядом с бинарником,
  который сносится первым же `cargo clean`.
- **Дефолт каталога чатов** сменился с `chat_files` на `chats`. Старый каталог на
  диске не удаляется и в наборы не попадает — он детектится как аномалия.

## 2. Модель снапшота

Один снапшот = один `manifest.json` + один или несколько объектов в S3. Файловые
наборы кладутся в общий `bundle.zip`; набор `database` (фаза 2) потребует
отдельного объекта, поэтому манифест с самого начала описывает **список
объектов**, а набор ссылается на объект через `object_index`.

```
manifest.json                    # первая запись архива
sets/<set_id>/<relative_path>    # файлы наборов
```

Ключи в бакете:

```
datasets/catalog.json
datasets/<instance_id>/<snapshot_id>/manifest.json
datasets/<instance_id>/<snapshot_id>/bundle.zip
```

`snapshot_id` = `<YYYYMMDDTHHMMSSZ>-<8hex>` — сортируется лексикографически по
времени и уникален.

**Манифест хранится дважды**: внутри zip (архив самодостаточен) и отдельным
объектом рядом (UI считает дифф, не скачивая бандл). Копия внутри zip не может
содержать собственный хеш, поэтому у неё `size_bytes`/`sha256` своего объекта
нулевые — заполненные значения несут внешний `manifest.json` и запись каталога,
именно по ним идёт проверка перед распаковкой.

### Диагностика источника (`SourceInfo`)

`instance_id` / `instance_label` / `instance_env`, `hostname`, `app_version`,
`git_commit`, `build_profile`, `schema_version` (номер миграции), `os`,
`data_root`, `database_path`, `config_path`, `captured_at`.

Плюс по каждому набору: исходный путь, `PathOrigin`, признак существования,
число файлов, суммарный размер, детерминированный хеш дерева, полное дерево
файлов и **список пропущенного** (`skipped`) с причинами — без него «файла нет в
архиве» выглядит как потеря данных.

Хеш дерева считается как sha256 над отсортированными по пути строками
`"<path>\0<size>\0<file_sha256>\n"` — не зависит ни от порядка обхода файловой
системы, ни от времени модификации.

### Каталог

`datasets/catalog.json` — единственный способ для принимающего экземпляра узнать,
какие снапшоты существуют: `sys_files_s3` локальна для донора, а листинга бакета
в S3-клиенте нет. Обновляется read-modify-write, как `plugins/catalog.json`, и
наследует то же ограничение: одновременная публикация с двух экземпляров может
потерять одну запись.

Деревья файлов в каталог не попадают — иначе объект разрастётся до мегабайтов.

**Ротация** `keep_per_instance` применяется только к снапшотам своего
`instance_id`. Чужие не трогаются никогда — иначе тестовый экземпляр при первой
же выгрузке снёс бы бэкапы рабочего.

## 3. Восстановление

1. **Предпросмотр** (`POST /api/sys/datasets/restore/preview`) — читается только
   манифест. Сравнение по **sha256**: размер служит предфильтром, mtime после
   копирования каталогов бесполезен. Классы: `Added` / `Modified` / `Identical` /
   `LocalOnly`.
2. **Режим**: `merge` — файлы бандла перезаписывают одноимённые, лишние локальные
   остаются; `replace` — набор становится точной копией, лишние удаляются, **кроме**
   путей под `exclude` дескриптора (`.obsidian/`, `.trash/`, `_templates/` в базе
   знаний — рабочее окружение Obsidian, а не данные).
3. **Автоснапшот** текущего состояния затронутых наборов в
   `<data_root>/backups/pre-restore-<ts>.zip`. Формат тот же, поэтому откат — это
   обычное восстановление из файла с `mode=replace`. Локально хранятся последние 10.
4. **Применение** — схема `quality::registry::upsert_authoring_bundle`, поднятая
   с уровня пакета на уровень каталога набора: staging рядом с целевым каталогом
   (`rename` не работает через границы томов, а при legacy-override наборы могут
   лежать на разных дисках) → `rename` цели в `.bak` → `rename` staging в цель.
5. **Горячие кэши** перезагружаются только после того, как все наборы легли на
   место: `reload_knowledge_base()`, `skills::reload()`, `quality::registry::reload()`.
6. **Откат** возвращает *все* затронутые наборы при любой ошибке — файловой или
   на перезагрузке кэша.

Перед применением сверяется sha256 бандла с записью каталога (**до** распаковки),
а из предпросмотра передаётся `expected_bundle_sha256` — чтобы применить ровно
тот архив, который был показан в диффе.

Пути из архива валидируются перед любой записью на диск: запрещены `..`,
абсолютные пути, буквы дисков, обратные слеши, пустые сегменты и имена с
завершающими точкой/пробелом (Windows молча их обрезает).

> **Windows.** Открытый Obsidian держит хендлы на файлы базы знаний и может
> сломать `rename`. Это приводит к штатному откату и сообщению «каталог занят
> другим процессом».

## 4. API

Все роуты под `require_admin`, scope `sys_datasets` (отдельно от `sys_s3_files`:
«посмотреть список файлов в бакете» и «перезаписать базу знаний» — права разной
разрушительности). Ошибка конфигурации S3 → **503**, не 500.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/sys/datasets/status` | наборы, пути, `PathOrigin`, счётчики, аномалии, карточка экземпляра |
| GET | `/api/sys/datasets/catalog` | снапшоты из `catalog.json` + локальный `instance_id` |
| POST | `/api/sys/datasets/snapshots` | запустить выгрузку → `202 {job_id}` |
| GET/DELETE | `/api/sys/datasets/snapshots/:id` | полный манифест / удалить |
| GET | `/api/sys/datasets/snapshots/:id/download` | скачать `bundle.zip` |
| POST | `/api/sys/datasets/restore/preview` | дифф |
| POST | `/api/sys/datasets/restore` | запустить восстановление → `202 {job_id}` |
| POST | `/api/sys/datasets/restore/upload` | импорт zip файлом (откат, S3 недоступен) |
| GET | `/api/sys/datasets/history` | журнал `sys_dataset_transfer_log` |
| GET | `/api/sys/datasets/jobs/active` | текущая операция или `null` |
| GET | `/api/sys/datasets/jobs/:job_id` | стадия, байты, результат, ошибка |
| POST | `/api/sys/datasets/jobs/:job_id/cancel` | прервать операцию |

**Выгрузка и восстановление — фоновые задачи с опросом.** Снимок базы это
`VACUUM INTO` нескольких гигабайт, сжатие и загрузка по частям, то есть минуты,
которых не переживёт ни один разумный HTTP-таймаут. Связка «увидел этот дифф —
подтвердил этот дифф» при этом сохраняется: её держит `expected_bundle_sha256`
внутри запроса, а не синхронность вызова.

Одновременно выполняется **не больше одной** операции переноса (снапшот и
восстановление работают с одними каталогами) — вторая получает **409**. Прогресс
двухуровневый: стадия (`Снимок БД (VACUUM INTO)`, `Выгрузка в S3`, …) и байты
внутри стадии; `bytes_total = 0` означает «объём заранее неизвестен», и UI
рисует бегущую полосу вместо выдуманного процента. Завершённые задачи живут в
памяти 30 минут, чтобы результат пережил перезагрузку вкладки.

Остальные операции (предпросмотр, удаление, скачивание архива) остаются
синхронными — они укладываются в один запрос.

## 6. Набор «База данных»

Набор `database` доступен наравне с файловыми, но устроен иначе в трёх местах.

**Снимок.** Живой `app.db` в режиме WAL консистентен только вместе с `-wal`, и
копия, снятая под нагрузкой, — мусор. Поэтому: `wal_checkpoint(TRUNCATE)` →
`PRAGMA integrity_check` на источнике (битую базу незачем ни выгружать, ни
хранить как резервную копию) → `VACUUM INTO` во временный файл под
`<data_root>/tmp/` → повторный `integrity_check` уже на полученном файле как на
самостоятельной базе. Временный файл убирается в любом исходе (`Drop` на
`DbSnapshotFile`).

**Доставка.** Отдельным объектом `database.db.gz`, потоком: файл → gzip → части
по 64 МиБ → S3. В память целиком не читается ни в одну сторону. На той же
проходке чтения считается sha256 несжатого файла (для `FileEntry` набора) —
второй проход по гигабайтам стоил бы дороже всей остальной подготовки. sha256
самого объекта считается по сжатым байтам. При скачивании сеть, подсчёт sha256 и
распаковка в staging-файл идут одним ограниченным по памяти конвейером — без
промежуточной записи `.gz` и его повторного чтения. Staging-файл допускается к
проверке SQLite и подмене только после совпадения sha256 всего объекта. Любая
ошибка или отмена выгрузки вызывает `AbortMultipartUpload`: незавершённая
загрузка остаётся в бакете невидимой и платной.

Многочастная загрузка потребовала подписи query-параметров в
`system/s3/client.rs` (`?uploads`, `?uploadId`, `?partNumber`) — раньше canonical
request строился с жёстко пустой query-строкой. Побочно это снимает ограничение
на `ListObjectsV2` и presigned-ссылки.

**Подмена файла.** Восстановление БД не подменяет файл на живом приложении: его
держит пул подключений, и на Windows переименовать поверх открытого файла нельзя,
а закрывать пул под работающими обработчиками означает, что часть запросов
увидит старую базу, часть новую. Поэтому восстановление кладёт готовый файл в
`<data_root>/db/pending_restore.db` и пишет маркер `pending_restore.json`
(откуда приехала база, чья схема, кто восстанавливал). Подмена происходит при
следующем старте процесса **до** открытия пула — шаг 1.5 в `main.rs`, до
`initialize_database()`. Прежняя база уезжает в
`<data_root>/backups/pre-restore-db-<ts>.db` переименованием (не копированием),
`-wal`/`-shm` удаляются, хранятся 2 последних. `RestoreResultDto.requires_restart`
показывается в UI отдельным сообщением.

Расхождение `schema_version` для БД — **блокирующее** предупреждение
(`db_schema_mismatch`): чужая схема плюс локальные миграции дают состояние,
которое никто не проверял. Для файловых наборов то же расхождение остаётся
обычным предупреждением.

Дифф по базе сравнивает **размеры, а не хеши**: `VACUUM INTO` перестраивает
страницы, поэтому даже снимок собственной базы дал бы «другой файл». Единственное
честное утверждение здесь — «база будет заменена целиком»; режим у набора только
`Replace`.

Лимит объёма — свой, `[datasets].max_db_gb` (по умолчанию 20).
`max_bundle_mb`/`[s3].max_upload_mb` относятся только к zip файловых наборов:
мерить потоковый объект лимитом in-memory архива бессмысленно.

> Копия манифеста **внутри** zip описывает только файловые наборы: она пишется до
> того, как объект базы выгружен. Полную картину несут внешний `manifest.json`
> рядом с бандлом и запись каталога — по ним и идёт восстановление.

**Фаза 3** (по необходимости): `task030_dataset_snapshot` — ночная автовыгрузка.
Номер зарезервирован; `publish::create_snapshot` не зависит от HTTP, поэтому
менеджер задачи будет тонкой обёрткой по образцу `task008_wb_prices.rs`.
Порог, после которого это становится обязательным: набор вложений > 100 МБ.

## 7. Режим технического обслуживания

Одной только очереди задач (`jobs.rs`: одна операция переноса за раз) мало —
она разводит переносы между собой, но никак не касается пользователей.
Для базы данных этого недостаточно, причём по разным причинам в двух случаях:

* **Выгрузка.** Целостности ничего не угрожает: `VACUUM INTO` берёт
  согласованный снимок, а в WAL-режиме читатель не блокирует писателей. Но
  долгий читатель не даёт checkpoint'у обрезать WAL, и под записью тот заметно
  распухает, плюс диск занят целиком минуты.
* **Восстановление.** Здесь дело не в производительности. Подмена файла
  происходит при следующем запуске, а всё, что пользователи запишут между
  подготовкой и перезапуском, уедет в архив вместе со старой базой — **молча**.
  Это и есть главный повод для режима.

Механика (`system/maintenance.rs` + `system/middleware/maintenance_gate.rs`):

| Свойство | Решение |
|---|---|
| Где хранится | `AtomicBool` + описание в памяти процесса. В БД нельзя: при восстановлении подменяется сама база. Перезапуск снимает режим — для автоматического включения это нужное поведение, для ручного — аварийный выход. |
| Кого пускает | Только администраторов. Плюс всегда открыты статика SPA, `/health`, `/api/system/maintenance` и роуты входа — иначе заглушку нечем показать, а админу неоткуда войти. |
| Кого закрывает | Всех остальных: вход (`login` отказывает **после** проверки пароля, иначе по коду ответа можно перебирать логины), любой прикладной роут и **внешний API** (`X-Api-Key`). Принять от 1С документ в базу, которую вот-вот заменят, — значит потерять его молча; 503 с `Retry-After` честнее. |
| Фоновые задачи | Операция с БД после включения maintenance ждёт завершения уже идущих регламентных задач и удерживает эксклюзивный барьер до конца передачи. Планировщик и ручной запуск новых задач в это окно не стартуют; внутренние циклы прунинга API-лога и флаша статистики БЗ пропускают запись. |
| Включение | Автоматически — операцией с набором `database`; вручную — тумблером на вкладке «Диагностика» страницы «Наборы данных». |
| Снятие | Выгрузка — аренда (`MaintenanceLease`) снимает режим сама при любом исходе, включая панику. Восстановление — `lease.keep()`, затем через 5 секунд graceful shutdown; NSSM автоматически поднимает процесс, bootstrap применяет `pending_restore`, а режим исчезает вместе со старым процессом. Снять его руками до рестарта нельзя (`requires_restart` → 409). |
| Чужой режим | Аренда не снимает режим, который включил не она: автоматическая операция внутри ручного обслуживания не откроет приложение по своему завершению. |
| Что видит человек | Причину работ, без всякого входа. Отказ 503 несёт тело `MaintenanceUnavailableDto` (`error: "maintenance"`, причина, время начала) — и от гейта, и от `login`; экран входа показывает ту же строку полосой поверху, опрашивая публичный статус. Голый код статуса человек читает как поломку. |
| Экраны | Не вошёл → обычный экран входа + полоса о работах (админу нужна форма, остальным — объяснение). Вошёл не-админ → полноэкранная заглушка с кнопкой выхода. Вошёл админ → приложение с плашкой сверху. Форму входа внутрь заглушки не вкладывать: `.login` — полноэкранный слой (`position: fixed`), он перекрывает карточку целиком. |

API: `GET /api/system/maintenance` (публичный),
`POST /api/system/maintenance/{enable,disable}` (admin).
